# Стандарты кода

Этот документ описывает принципы, которым следует код проекта. Применяется
ко всему новому коду. При ревью — проверять соответствие этому документу.

## Базовые принципы

### SOLID

**S — Single Responsibility Principle (SRP)**
Один класс — одна причина для изменения. Если класс делает и валидацию,
и маппинг, и обращение к БД — разделить.

В этом проекте это означает:
- Контроллеры только принимают/отдают HTTP, делегируют сервисам
- Сервисы содержат бизнес-логику
- Репозитории только работают с БД
- Мапперы только конвертируют между DTO и доменом
- Валидация — через Bean Validation (аннотации на DTO)

**O — Open/Closed Principle**
Код открыт для расширения, закрыт для изменения. Добавление нового
типа узла (`NodeType`) или ребра (`EdgeType`) не должно требовать правок
в существующих классах. Используем стратегии, enum'ы, полиморфизм.

Пример: `StatusCalculationService` должен уметь обрабатывать новый тип ребра
через регистрацию стратегии, а не через `if (type == NEW_TYPE)`.

**L — Liskov Substitution Principle**
Подкласс должен быть полностью заменяем родителем. В Java records это
менее актуально, но касается интерфейсов: реализация интерфейса не должна
сужать контракт.

**I — Interface Segregation Principle**
Лучше несколько маленьких интерфейсов, чем один большой. Не заставлять
реализации поддерживать методы, которые им не нужны.

**D — Dependency Inversion Principle**
Зависеть от абстракций, не от реализаций. Сервисы зависят от интерфейсов
репозиториев (если репозиториев больше одной реализации) или от
конкретных классов репозиториев (если одна реализация — что ок для этого
проекта, не делать интерфейсы ради интерфейсов).

### KISS (Keep It Simple, Stupid)
Самое простое решение, которое работает. Не закладывать гибкость "на всякий
случай". Лучше переписать через месяц, когда появится реальный use-case.

### DRY (Don't Repeat Yourself) — с оговоркой
Не дублировать **знание**. Но три похожих куска кода — ещё не повод выносить
в общий метод, если они *случайно* похожи и могут разойтись. Правило трёх:
дублирование становится проблемой на третьем повторении.

### YAGNI (You Aren't Gonna Need It)
Не писать код "на будущее". Не добавлять параметры методов "вдруг понадобится".
Не создавать абстракции без текущего use-case. Roadmap есть — ему и следуем.

### Composition over Inheritance
Наследование — только там, где есть явная is-a связь. В остальных случаях —
композиция. В Spring-коде наследование почти не нужно.

## Правила Java-кода

### Иммутабельность по умолчанию
- Предпочитать `record` классам для DTO, value objects, доменных моделей без
  поведения
- Поля классов — `private final` всегда, если нет явной причины иначе
- Коллекции — возвращать неизменяемые (`List.copyOf(...)`, `Collections.unmodifiableList(...)`)
- Не мутировать входные параметры метода

### Обработка `null`
- Методы, которые могут не найти результат — возвращают `Optional<T>`,
  не `null`
- Коллекции — **никогда** не возвращать `null`, только пустой список/множество
- Параметры методов — по умолчанию считаются non-null. Если `null` допустим —
  явно аннотировать и документировать
- `Optional` использовать только как возвращаемое значение, **не** как
  поле класса и **не** как параметр метода

### Именование

**Классы:**
- Существительные: `NodeService`, `EdgeRepository`, `TopicController`
- Суффикс по роли: `*Service`, `*Repository`, `*Controller`, `*Mapper`,
  `*Config`, `*Exception`
- DTO: `CreateNodeRequest`, `NodeResponse`, `NodeDto` — выбрать одну
  конвенцию и держаться. Для проекта: `*Request` / `*Response`

**Методы:**
- Глаголы: `createNode`, `findById`, `calculateStatus`
- Булевы: `isRefuted`, `hasChildren`, `canBeRemoved`
- Find vs Get: `findById` → `Optional<T>`, `getById` → `T` или исключение

**Переменные:**
- Полные имена, без сокращений: `nodeRepository`, не `nodeRepo`
- Исключения: общепринятые короткие (`id`, `dto`, `req`, `resp` в узком
  scope)

**Константы:**
- `UPPER_SNAKE_CASE`
- Магические числа — в константы всегда, кроме совсем очевидных (0, 1, -1)

### Структура класса (порядок)
1. Константы (`static final`)
2. Поля
3. Конструктор(ы)
4. Публичные методы
5. Приватные методы (в порядке использования)

### Ограничения размера
- Метод: до 20-30 строк. Если больше — обычно можно выделить приватные методы
- Класс: до 200-300 строк. Больше — повод подумать о разделении
- Параметры метода: до 4-5. Больше — передавать объект-параметр

### Обработка исключений
- **Никогда** не ловить `Exception` или `Throwable` без крайней необходимости
- Ловить только те исключения, которые знаешь как обработать
- **Никогда** не глотать исключения: `catch (Exception e) {}` — запрещено
- Checked исключения оборачивать в unchecked в сервисном слое
- Бросать доменные исключения (`NodeNotFoundException`, `InvalidEdgeException`),
  не стандартные (`RuntimeException`, `IllegalStateException` — только для
  программных ошибок)
- Сообщения исключений — по-русски, информативные: *"Узел с id=%s не найден в теме %s"*

### Логирование

**Уровни:**
- `ERROR` — что-то сломалось, нужно внимание
- `WARN` — подозрительная ситуация, но работа продолжается
- `INFO` — важные бизнес-события (создание темы, пересчёт графа)
- `DEBUG` — детали для разработки
- `TRACE` — совсем мелкие детали

**Правила:**
- Логи на русском
- Использовать параметризацию SLF4J: `log.info("Создан узел id={} в теме {}", nodeId, topicId)`,
  **не** конкатенацию строк
- Не логировать чувствительные данные (токены, пароли)
- В `ERROR` и `WARN` — всегда передавать исключение последним параметром:
  `log.error("Ошибка пересчёта статусов для темы {}", topicId, ex)`
- Не логировать одно и то же на разных уровнях стека

## Комментарии в коде

### Когда комментарии нужны
- **Объяснение "почему", а не "что"**: `// Используем для обхода бага в драйвере JDBC при bulk insert`
- **Неочевидная бизнес-логика**: `// INVALIDATES от STANDING-источника безусловно даёт REFUTED, даже если есть STANDING-поддержки (ADR-007)`
- **Ссылки на тикеты/документы**: `// См. ADR-002 в docs/decisions.md`
- **Предупреждения**: `// ВНИМАНИЕ: порядок важен, см. gotchas.md#transaction-order`
- **TODO с контекстом**: `// TODO: вынести в отдельный сервис после реализации Этапа 5`

### Когда комментарии НЕ нужны
- Если код самодокументируемый: `// увеличиваем счётчик` перед `counter++` — мусор
- Если комментарий повторяет имя метода: `// создаёт узел` перед `createNode()`
- Закомментированный код — **никогда**, git хранит историю
- JavaDoc ради JavaDoc — только для нетривиальных публичных методов и API

### JavaDoc
- Только для сложных публичных методов, где неочевидно поведение
- На русском
- Обязательно документировать:
  - Что возвращается, если не найдено
  - Бросаемые доменные исключения
  - Побочные эффекты (запись в БД, отправка событий)
- Не писать `@param id идентификатор` — это бесполезно

Пример хорошего JavaDoc:
```java
/**
 * Пересчитывает статус узла на основе всех входящих рёбер.
 * Каскадно обновляет статусы зависимых узлов, если статус данного изменился.
 *
 * @throws NodeNotFoundException если узел с заданным id не существует
 * @throws GraphCycleException если обнаружен цикл в графе во время обхода
 */
NodeStatus recalculateStatus(UUID nodeId);
```

## Транзакции

- `@Transactional` — только на сервисном слое, не на контроллерах и не на
  репозиториях
- `@Transactional(readOnly = true)` — для методов только-чтения (оптимизация)
- **НИКОГДА** не ставить `@Transactional` на `@Scheduled` методы напрямую —
  см. `gotchas.md`
- Транзакция должна быть как можно короче — не делать внутри неё HTTP-вызовы,
  чтение файлов, долгие вычисления
- Избегать вложенных транзакций, если не понимаешь точно, что делаешь

## Audit logging (ADR-043 Amendment 3)

Mutation сервисы пишут в `audit_log` синхронно в той же транзакции что
и main flow. Использовать builder-helpers из `AuditLogService` -
**не** строить `Map<String, Object>` вручную через `LinkedHashMap` +
`put`.

### Snapshot для CREATE/DELETE

```java
Map<String, Object> snapshot = AuditLogService.snapshot()
    .put("title", book.title())
    .put("visibility", book.visibility())
    .build();
auditLogService.logCreate(BOOK, book.id(), null, null, userId, snapshot);
```

`put` принимает null - сохраняет ключ с null-value (важно для full
snapshot чтобы видеть какие поля были null до удаления). Для enum
вызывать `.name()` явно на caller-стороне.

### Diff для UPDATE

```java
Map<String, FieldDiff> diff = AuditLogService.diff()
    .compare("title", before.title(), after.title())
    .compare("body", before.body(), after.body())
    .build();
if (!diff.isEmpty()) {
    auditLogService.logUpdate(...);
}
```

`compare()` сам пропускает поля где before == after через
`Objects.equals` - **не** писать `if (!Objects.equals(...)) diff.put(...)`
руками.

### null vs ""

null значения в snapshot/diff сериализуются как JSON null (не "")
для отличия absent от empty-string. Это семантически важно при
чтении audit log: `field.old == null` = поле было absent,
`field.old == ""` = поле было пустой строкой.

## Тесты

### Именование тестов
Формат: `методTested_условие_ожидаемыйРезультат`

Примеры:
- `createNode_whenTopicExists_returnsCreatedNode`
- `createNode_whenTopicNotFound_throwsException`
- `recalculateStatus_withConflictingEdges_returnsDisputed`

### Структура теста — AAA
- **Arrange** — подготовка данных
- **Act** — вызов тестируемого метода
- **Assert** — проверка результата

Разделять пустой строкой, если помогает читаемости. Не комментариями
`// given`, `// when`, `// then` — это шум.

### Что тестировать
- Сервисы — в первую очередь, через unit-тесты с моками репозиториев
- Репозитории — интеграционные тесты через Testcontainers
- Контроллеры — интеграционные тесты через `MockMvc` + Testcontainers
- Алгоритм пересчёта статусов — максимально детально, все граничные случаи

### Чего избегать в тестах
- Тесты с пустым `@Test` — лучше удалить
- Тесты, которые тестируют моки, а не код
- Тесты с `Thread.sleep()` — использовать Awaitility
- Тесты, зависящие от порядка выполнения
- Общее состояние между тестами (статические поля)

## Код-ревью

При ревью чужого (или своего) кода проверять в следующем порядке:

1. **Правильность** — делает ли код то, что должен?
2. **Соответствие архитектуре** — не нарушает ли `decisions.md`?
3. **Соответствие стандартам** — этот файл
4. **Антипаттерны** — см. `antipatterns.md`
5. **Тесты** — есть ли покрытие ключевой логики?
6. **Читаемость** — понятно ли через месяц?

Формат комментариев ревью (при общении с пользователем):
- 🔴 Критично — нельзя мерджить
- 🟡 Важно — желательно исправить
- 🟢 Совет — на усмотрение автора
