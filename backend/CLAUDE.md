# Argument Map — Backend (Claude Code config)

## Контекст: это монорепа

Этот `CLAUDE.md` — конфиг для работы над **бэкенд-частью** проекта
Argument Map. Полная структура репозитория описана в `../README.md`.

Правила:
- Работать **только** в пределах папки `backend/`. Не создавать, не
  редактировать и не удалять файлы в корне репы и в `../frontend/`
  без явного запроса пользователя.
- Общая документация проекта лежит в `../docs/` — её читаем, но
  редактируем только когда изменения явно относятся к продукту в целом
  (новый ADR, обновление roadmap, запись в progress).
- Бэкенд-специфичная документация — в `backend/docs/`.
- Корневой `docker-compose.yml` общий — не копировать в `backend/`.

## О проекте

API-first приложение для построения карт аргументации (argument mapping).
Позволяет строить графы дискуссий: вопросы, тезисы, аргументы, контр-аргументы,
источники и мнения учёных. Визуализация — позже на фронте (Miro/Obsidian-подобный UI).

Первый use-case — разбор религиозных (исламских) вопросов, но архитектура
предметно-нейтральна: подходит для любых дискуссий.

## Стек

- **Java 21**
- **Spring Boot 3.3+**
- **PostgreSQL 16** (хранение графа как nodes + edges)
- **Liquibase** — миграции БД
- **JDBC Template** — доступ к БД напрямую, без JPA/Hibernate
- **Testcontainers** — интеграционные тесты
- **Maven**
- **Docker Compose** — локальный Postgres (в корне репы)

## Работа с документацией (КРИТИЧНО)

Эти правила обеспечивают непрерывность работы между сессиями. Контекст одной
сессии теряется, поэтому документация — это "память" проекта. Следовать строго.

### В начале каждой сессии
1. Прочитать `../docs/progress.md` — последние 2-3 записи
2. Прочитать `../docs/roadmap.md` — найти текущую задачу
3. Прочитать `../docs/decisions.md` — не нарушать принятые решения
4. Прочитать `../docs/gotchas.md` — не наступить на известные грабли
5. Кратко озвучить пользователю: *"Вижу, последний раз делали X, следующая
   задача — Y. Продолжаем?"*

### По ходу работы

Документация - "память" проекта между сессиями. Если её не вести
ходом, в новой сессии теряется контекст и решения переоткрываются
заново. **После каждого `feat`/`fix` коммита** обязательный чек-лист:

#### Чек-лист "что документировать" после коммита

| Что произошло в коммите | Что обновить |
|---|---|
| Закрыт пункт roadmap | `roadmap.md` - проставить `[x]` |
| Принято решение между альтернативами (где была дилемма) | `decisions.md` - **новый ADR** с разделами: Контекст / Решение / Альтернативы / Последствия |
| Миграция БД, изменение доменной модели | `decisions.md` - ADR + `architecture.md` - упомянуть |
| Изменилась схема `Node`/`Edge`/`Topic`/`User` | `architecture.md` - доменные сущности |
| Новый/изменённый REST endpoint, новые поля DTO | `api-contract.md` - описание + история изменений |
| Поймал баг через линтер/тесты/IT который **может повториться** | `gotchas.md` - симптом + причина + решение |
| Новое доменное понятие (термин из бизнес-области) | `glossary.md` |
| Изменились бэкенд-правила (стандарты Java/Spring/Liquibase) | `backend/docs/` |

**Тревожные триггеры для ADR** - почти наверняка нужен ADR если в
коммите было:
- Выбор между ≥2 рассмотренных подходов (rejected alternatives есть)
- Изменение схемы БД (миграция Liquibase)
- Изменение контракта API (новое поле/эндпоинт)
- Решение "не делаем X сейчас, отложим до Y" (явный YAGNI)
- Введение новой инфраструктурной системы

**Тревожные триггеры для gotcha** - если что-то из этого ловили:
- "Failsafe не запускает IT" / "Liquibase не применяет миграцию"
- Spring/Hibernate/JDBC "ведёт себя не как ожидалось"
- Странные ошибки типов в Java/Spring (Instant vs OffsetDateTime)
- Тесты ломаются от чего-то что выглядит несвязанным

Не должно быть так что фикс делается, gotcha не записан, через две
недели наступаем на тех же граблях.

#### Не дожидайся конца сессии для документации

Не "сделаю всё за раз в `progress.md`" - частично это правда (журнал
сессии), но **ADR / gotcha / api-contract обновляются по ходу**, в
коммите который к ним относится. Атомарная ревизия: один коммит =
одно изменение + его документация. Если ADR относится к коммиту X,
то в коммите X должен лежать обновлённый `decisions.md` (либо
отдельным `docs:` коммитом сразу следом).

### Эволюция документов

Документы проекта — живые, но разные документы имеют разные правила
эволюции. Следовать им строго.

#### `roadmap.md`

Roadmap — карта, а не рельсы. Отражает текущее понимание плана,
обновляется по мере работы.

**Можно без спроса:**
- Проставлять `[x]` на выполненных пунктах
- Добавлять обнаруженные подзадачи в текущий этап
- Добавлять `TODO` пункты в этапы, которые ещё не начаты
- Разбивать слишком крупные пункты на подпункты
- Дописывать уточнения в формулировки существующих пунктов

**Нужно обсудить с пользователем перед изменением:**
- Удаление пункта из roadmap
- Перенос пункта между этапами
- Добавление целого нового этапа
- Изменение порядка этапов
- Отказ от ранее запланированной функциональности
- Радикальное изменение подхода к уже запланированному

**Как оформлять добавления:**
- Новые подзадачи добавлять в конец соответствующего этапа
- Если подзадача родилась из проблемы — рядом короткая заметка почему
  (например: `- [ ] Вынести GraphLoader в отдельный сервис
  (в GraphService стало >300 строк, нарушает SRP)`)
- Крупные дополнения также упоминать в записи сессии в `../docs/progress.md`,
  в разделе "Решения"

**Правило эволюции vs хаоса:**
Если дополнение делается "потому что полезно прямо сейчас" — добавляй.
Если дополнение меняет направление проекта или затрагивает уже принятые
ADR — останови работу и обсуди с пользователем.

#### `gotchas.md`

Добавлять свободно по мере открытий. Каждый раз, когда что-то
потратило время на дебаг и может повториться — записывай. Чем
больше `gotchas.md`, тем ценнее становится проект для будущих сессий.
Старые записи не редактировать без причины — только если решение
изменилось или дополнилось.

#### `decisions.md` (ADR)

- Новые ADR добавлять свободно, с возрастающим номером
- **Старые ADR никогда не редактировать** (кроме исправления опечаток)
- Если решение отменяется или заменяется — создать новый ADR со
  статусом `заменяет ADR-N` или `отменяет ADR-N`
- Перед принятием ADR, противоречащего существующему — остановиться
  и обсудить с пользователем
- ADR принимаются не только по крупным решениям, но и по неочевидным
  техническим выборам (например: "почему выбрали именно такой формат
  id для changeset'ов Liquibase")

#### `glossary.md`

Новые термины добавлять свободно. Если в коде или обсуждении появляется
термин, который может быть неочевиден — сразу в глоссарий. Особенно
важно для доменных терминов (из исламского контекста, из теории
аргументации). Существующие определения уточнять можно, но не менять
радикально без обсуждения.

#### `architecture.md`

Изменять **с осторожностью**. Это документ, описывающий "как всё
устроено на высоком уровне" — частые изменения означают, что архитектура
неустойчива.

**Можно без спроса:**
- Уточнять формулировки существующих разделов
- Добавлять детали к уже описанным сущностям (новые поля, связи)
- Исправлять расхождения с реальным кодом

**Обсудить с пользователем:**
- Добавление новой доменной сущности
- Изменение принципов хранения (например, отказ от дискриминатора)
- Изменение алгоритма пересчёта статусов
- Любое изменение, которое делает существующий код "неправильным"

#### `api-contract.md`

Изменения **только** при явном добавлении или изменении эндпоинта.
Это источник истины для контракта с фронтом — спонтанные изменения
ломают доверие к документу.

**Правила:**
- Каждый новый эндпоинт → запись в соответствующем разделе
- Каждое изменение существующего эндпоинта → запись + строка в таблице
  "История изменений контракта" внизу файла
- Breaking change → обсуждение с пользователем перед изменением
  (см. раздел "Версионирование" в `docs/api-design.md`)
- OpenAPI-спецификация (`/v3/api-docs`) должна соответствовать этому
  документу. Если расходятся — это баг, фиксить

#### `progress.md`

Только добавление новых записей в начало файла (новые сессии — сверху).
Старые записи **не редактировать** — это журнал, исторический документ.
Если что-то в старой записи было неверно — можно добавить комментарий
в новой записи, но не переписывать прошлое.

### В конце каждой сессии (ОБЯЗАТЕЛЬНО)
Перед завершением создать запись в `../docs/progress.md`:

```markdown
## YYYY-MM-DD — Сессия N (backend)
### Сделано
- конкретные выполненные задачи со ссылками на файлы/коммиты

### Решения
- принятые по ходу решения (если достойно ADR — также в decisions.md)

### Проблемы
- с чем столкнулись, как решили (если не решили — пометить "открыто")

### Следующий шаг
- конкретная следующая задача, чтобы новая сессия начала сразу с неё
```

**Помечать сессии префиксом `(backend)`**, чтобы в общем журнале было видно,
к какой части монорепы относится запись. Когда появится фронт — там будет
`(frontend)`.

**Правило:** запись должна быть такой, чтобы новая сессия могла прочитать её
и продолжить работу без дополнительных вопросов пользователю.

### При приближении к лимиту контекста
Если чувствуешь, что контекст заполняется — **не дожидаясь просьбы** предложи
пользователю сохранить состояние в `progress.md` максимально подробно, включая
все незавершённые мысли и следующий конкретный шаг.

## Соглашения по коду

### Общие правила
- **Язык:** все комментарии, логи, JavaDoc — на русском. Имена классов, методов, переменных — на английском.
- **JavaDoc:** только для нетривиальной и сложной логики. Не писать JavaDoc ради JavaDoc.
- **Комментарии:** только полезные, объясняющие *почему*, а не *что*. Если код самодокументируемый — комментарии не нужны.
- **Импорты:** использовать импорты вместо полных квалифицированных имён классов.

### Liquibase
- **Автор миграций всегда:** `Abdula Basnukaev`
- Формат changeset id: `YYYYMMDD-NN-short-description` (например, `20260413-01-create-topics-table`)
- Каждая миграция — отдельный файл в `src/main/resources/db/changelog/changes/`
- Мастер-файл: `src/main/resources/db/changelog/db.changelog-master.xml`
- Использовать `<rollback>` там, где это имеет смысл
- Индексы создавать в той же миграции, что и таблицу, если они очевидны

### База данных
- **Без JPA/Hibernate.** Только JDBC Template + ручной маппинг через RowMapper.
- Именование таблиц и колонок — `snake_case`
- Первичные ключи — UUID (`uuid` тип PostgreSQL)
- Timestamps — `timestamptz`, с дефолтом `now()` где уместно
- Soft delete пока не делаем — только hard delete, история через `revisions`

### Структура пакетов
```
ru.basnukaev.argumentmap
├── config          — Spring-конфигурация
├── domain          — модели предметной области (records/классы)
├── repository      — JDBC-репозитории
├── service         — бизнес-логика
├── web             — REST-контроллеры, DTO, мапперы
│   ├── controller
│   ├── dto
│   └── mapper
└── exception       — кастомные исключения + обработчики
```

### Тесты
- **Интеграционные тесты** — через Testcontainers (PostgreSQL), не H2
- Тесты именовать по паттерну `ClassNameTest` / `ClassNameIT`
- Использовать DBRider для подготовки данных там, где это упрощает тест
- Минимум: покрыть сервисы бизнес-логики и репозитории

## Локальная разработка

### Запуск Postgres
Выполняется **из корня репы**, не из `backend/`:
```bash
cd ..          # из backend/ → в корень
docker compose up -d
```
Postgres будет доступен на `localhost:5432`, база `argumentmap`, user/pass `argmap/argmap`.

### Сборка и запуск
Из папки `backend/`:
```bash
./mvnw clean install
./mvnw spring-boot:run
```

### Тесты
```bash
./mvnw test           # unit
./mvnw verify         # + integration
```

## Работа с задачами

Следуем task-driven подходу: каждая крупная задача оформляется как запись в
`../docs/roadmap.md` с чек-листом подзадач. По мере выполнения — отмечать.

## Что НЕ делать

- Не использовать JPA/Hibernate
- Не использовать Lombok без крайней необходимости (предпочитать Java records)
- Не добавлять зависимости без обсуждения
- Не писать бесполезные комментарии вида `// увеличиваем счётчик`
- Не коммитить закомментированный код
- Не лезть в `../frontend/` и корень репы без явного запроса

## Git-коммиты

Используем Conventional Commits с scope для монорепы:
- `<тип>(backend): описание`
- Типы: feat, fix, chore, docs, refactor, test, style, perf, build, ci
- Примеры:
    - `feat(backend): add POST /api/v1/topics endpoint`
    - `chore(backend): bump spring boot to 3.3.5`
    - `docs: update ADR-004`
- Scope `(backend)` обязателен для изменений в backend/
- Scope не нужен для изменений в корне репы или общей документации
