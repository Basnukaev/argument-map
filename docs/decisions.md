# Архитектурные решения (ADR)

Записи о принятых решениях в формате ADR-lite (Architecture Decision Records).
Новые ADR — **снизу**, с возрастающим номером. Не переписывать старые —
если решение отменяется, добавлять новый ADR со статусом "отменяет ADR-N".

Формат:
```
## ADR-NNN: Краткое название
**Дата:** YYYY-MM-DD
**Статус:** принято | отменено | заменено ADR-X
**Контекст:** какая проблема решается
**Решение:** что решили делать
**Причины:** почему именно так
**Последствия:** что это влечёт (плюсы и минусы)
```

> **Примечание о порядке:** записи нумеруются по порядку принятия
> решения, но физически в файле могут идти не строго по возрастанию
> номера — ориентируйся на даты. Это нормально: ADR — исторический
> документ, порядок добавления = порядок принятия.

## ADR-001: JDBC Template вместо JPA/Hibernate
**Дата:** 2026-04-13
**Статус:** принято
**Контекст:** нужен слой доступа к БД для работы с графом аргументов

**Решение:** использовать Spring JDBC Template + ручные RowMapper'ы.
Не использовать JPA, Hibernate, Spring Data JPA.

**Причины:**
- Привычный стек для разработчика (как в проекте CREW)
- Полный контроль над генерируемым SQL — важно для графовых запросов
- Нет магии ленивой загрузки, N+1 проблем, кеша первого уровня
- Предсказуемое поведение транзакций
- Проще интеграционные тесты — меньше "магии"

**Последствия:**
- (+) Явный SQL, легко оптимизировать графовые обходы
- (+) Нет проблем с ленивой загрузкой рёбер/узлов
- (−) Больше бойлерплейта на CRUD — принимаем как цену

## ADR-002: Source и Authority — справочники, а не узлы графа
**Дата:** 2026-04-13
**Статус:** принято
**Контекст:** нужно решить, как хранить источники (хадисы, книги) и
мнения учёных — как узлы графа или отдельно

**Решение:** `sources` и `authorities` — отдельные таблицы-справочники.
Связь с узлами — через M:N таблицы `node_sources` и `node_authorities`
с дополнительными метаданными (цитата, контекст, позиция).

**Причины:**
- Один хадис может цитироваться в десятках тем — не хотим дублирования
- У учёного есть свой профиль (эпоха, мазхаб, биография) — это не "аргумент"
- Источники и авторитеты должны искаться независимо от конкретных тем
- Справочники переиспользуются между пользователями и темами

**Последствия:**
- (+) Нет дублирования данных об источниках и учёных
- (+) Возможен независимый поиск/фильтрация по справочникам
- (+) Можно строить статистику "на какие хадисы чаще ссылаются"
- (−) Отдельная логика для привязки источников к узлам (M:N таблицы)

## ADR-003: Граф в двух таблицах (nodes + edges) с дискриминатором
**Дата:** 2026-04-13
**Статус:** принято
**Контекст:** нужно выбрать способ хранения графа в PostgreSQL

**Решение:** две таблицы — `nodes` (все узлы любого типа) и `edges` (все рёбра
любого типа). Тип различается через колонку-дискриминатор (`node_type`,
`edge_type`). Не создавать отдельные таблицы под каждый тип узла/ребра.

**Причины:**
- Гибкость: новый тип узла или связи добавляется без миграции схемы
- Простота графовых запросов: один JOIN вместо UNION по нескольким таблицам
- Количество типов небольшое и стабильное (4-5 типов узлов, 5 типов рёбер)
- Поля у всех типов узлов почти одинаковые (`content`, `status`, `weight`)

**Последствия:**
- (+) Простая схема, простые запросы
- (+) Легко добавлять новые типы узлов и связей
- (−) Нельзя делать тип-специфичные NOT NULL constraints на уровне БД —
  валидация в сервисном слое
- (−) Если у какого-то типа узла появится много специфичных полей — придётся
  использовать `jsonb` колонку или выделять в отдельную таблицу

## ADR-004: Maven вместо Gradle
**Дата:** 2026-04-13
**Статус:** принято
**Контекст:** нужно выбрать систему сборки для Java/Spring Boot бэкенда

**Решение:** использовать Maven (с Maven Wrapper). Не использовать Gradle.

**Причины:**
- Привычный стек для разработчика (аналогичная конфигурация в проекте CREW)
- Декларативный `pom.xml` проще для чтения и поддержки в проекте
  без сложной кастомизации сборки
- Максимальная совместимость с экосистемой Spring Boot — примеры,
  документация, плагины в первую очередь поддерживают Maven
- Maven Wrapper (`mvnw`) обеспечивает воспроизводимую сборку без
  глобальной установки Maven

**Последствия:**
- (+) Меньше порог входа — стандартный XML-конфиг без Groovy/Kotlin DSL
- (+) Предсказуемое поведение без "магии" Gradle-кеша
- (−) XML-конфигурация более многословна, чем Gradle DSL
- (−) Инкрементальная сборка медленнее чем у Gradle — для нашего
  размера проекта несущественно

## ADR-005: Монорепа с независимыми backend/ и frontend/
**Дата:** 2026-04-13
**Статус:** принято
**Контекст:** проект состоит из двух технологически разных частей —
Java/Spring-бэкенд и будущий JS/TS-фронтенд. Нужно решить, хранить их
в одном репозитории или в разных.

**Решение:** монорепа с двумя независимыми подпапками — `backend/` и
`frontend/`. Без специализированных инструментов монорепы (Nx, Turborepo,
Bazel). Каждая часть имеет свой build-инструмент, свои зависимости, свои
тесты. Общая документация продукта — в корневом `docs/`. Технологически
специфичная — в `backend/docs/` и `frontend/docs/`.

**Причины:**
- Одна история изменений — удобно отслеживать совместные изменения
  (например, новый эндпоинт + клиент для него в одном PR)
- Общие решения (архитектура, термины, ADR) живут в одном месте
- Инфраструктура (`docker-compose.yml`) общая — Postgres нужен и беку
  для работы, и фронту для e2e-тестов
- Специализированные инструменты монорепы — оверкилл для двух подпроектов
  на разных языках без shared-кода
- Простая модель: каждая часть независима, можно работать над одной, не
  трогая другую

**Последствия:**
- (+) Один `git clone`, один PR на сквозные изменения
- (+) Общая документация видна обеим частям
- (+) Нет сложности настройки (никаких workspace-конфигов, lerna, nx.json)
- (−) CI должен уметь собирать обе части, детектируя изменённые пути
- (−) Claude Code нужно запускать внутри конкретной подпапки
  (`cd backend && claude`), не в корне — это описано в `README.md`
- (−) При росте проекта возможно потребуется миграция на инструменты
  монорепы — принимаем как цену простоты на старте

## ADR-006: `createdBy` через HTTP-заголовок `X-User-Id` до появления авторизации
**Дата:** 2026-05-03
**Статус:** принято
**Контекст:** колонки `created_by` во всех таблицах уже `NOT NULL` (Этап 1
закрыт), но полноценная авторизация (Spring Security, JWT) запланирована
только на Этап 6. На Этапе 3 нужно начать писать сервисный слой с
операциями мутации (`createTopic`, `createNode`, `createEdge`,
`createRevision`), и каждой из них требуется UUID автора. Откуда брать
этот UUID сейчас?

**Решение:** контроллеры читают `X-User-Id` (UUID) из HTTP-заголовка,
валидируют существование такого пользователя в таблице `users` и
прокидывают `UUID userId` явным параметром в методы сервисов, требующие
авторства. Сервисы не знают про HTTP-контекст. Тесты сервисного слоя
получают `userId` напрямую как аргумент. Для интеграционных и e2e-сценариев
пользователь в `users` создаётся фикстурой / отдельной seed-миграцией.

**Причины:**
- Минимальная заглушка под будущий Spring Security: при его появлении
  поменяется только источник UUID — контроллер достаёт его из
  `Authentication`/`Principal` вместо заголовка, контракты сервисов
  не меняются. Никакого `Optional<UUID>`, никаких "system user" хардкодов
- Не пускаем `createdBy` в тело запроса (антипаттерн — клиент сможет
  писать от чужого имени; при появлении авторизации придётся ломать API)
- Не плодим "одного системного пользователя" — терялась бы реальная
  история авторства, при апгрейде до multiuser пришлось бы делать
  data-миграцию с разделением
- Не делаем ленивую регистрацию по `username` — вне цели MVP, плодит
  состояние, которое потом сложно ломать

**Последствия:**
- (+) API сервисов финальный — при подключении Security сигнатуры не
  меняются
- (+) Тесты сервисов остаются простыми: `userId` — обычный параметр
- (+) Можно тестировать multiuser-сценарии (несколько `X-User-Id`) уже
  на Этапе 3
- (+) Контроллеры получают чёткую обязанность: распарсить заголовок,
  валидировать пользователя, прокинуть UUID. Это естественная граница
  под будущий `@AuthenticationPrincipal`
- (−) Контроллер делает один лишний запрос к `users` для валидации
  (можно кешировать, но для MVP не нужно)
- (−) Любой клиент, знающий чужой UUID, пишет от его имени. Принимаем
  как временный риск — это **не** прод-механизм, должен быть закрыт
  на Этапе 6 одновременно с появлением Spring Security
- (−) Заголовок `X-User-Id` нужно явно прописать в `api-contract.md`
  как требуемый для всех мутирующих эндпоинтов

## ADR-007: Вклад типов рёбер в алгоритм пересчёта статусов
**Дата:** 2026-05-03
**Статус:** принято
**Контекст:** в проекте 5 типов рёбер (`SUPPORTS`, `REFUTES`,
`QUALIFIES`, `INVALIDATES`, `RESPONDS_TO`), а MVP-алгоритм пересчёта
статусов в `architecture.md` описан в терминах "supports" / "refutes".
Нужно зафиксировать вклад каждого типа, иначе сервис `StatusCalculation`
будет неполным/неоднозначным.

**Решение:**

| Тип ребра | Вклад в статус |
|---|---|
| `SUPPORTS` | поддержка |
| `REFUTES` | опровержение |
| `INVALIDATES` | "жёсткий kill": если источник `STANDING`, цель → `REFUTED` безусловно (бьёт даже стену `STANDING` supports) |
| `QUALIFIES` | не влияет на статус (только семантика "уточняет применимость") |
| `RESPONDS_TO` | не влияет на статус (организационная связь "это ответ на это") |

**Причины:**
- Соответствует языку `architecture.md`: "INVALIDATES действует на ребро
  или узел как 'жёсткое' опровержение, сильнее чем REFUTES"
- `QUALIFIES` ≠ `REFUTES` семантически: уточнение области применения
  тезиса не делает его ложным, поэтому в MVP не вмешиваем в алгоритм
- `RESPONDS_TO` — диалоговая структура ("это реплика-ответ на эту
  реплику"), не оценочная связь. На вопрос можно "ответить" разными
  способами, в том числе сомнениями
- `INVALIDATES` как kill-switch (а не просто "сильный refute") даёт
  однозначную семантику для мета-аргументов из изначального примера в
  `architecture.md` ("сказанное в противовес учёному нерелевантно")
- KISS: `QUALIFIES` и `RESPONDS_TO` остаются "значимыми, но не
  алгоритмическими" — их можно повысить до influencing-типов с весами
  без миграции схемы, когда появится продвинутая версия алгоритма (Dung)

**Последствия:**
- (+) Алгоритм пересчёта компактен: учитывает только 3 типа из 5
- (+) `QUALIFIES`/`RESPONDS_TO` остаются полноценными гражданами графа
  (показываются на UI, попадают в `GET /graph`), но не вызывают
  каскадных пересчётов
- (+) Семантика `INVALIDATES` отделена от обычного `REFUTES` — это
  отражает реальное мета-уровневое использование
- (−) `QUALIFIES`-связи требуют отдельного UI-объяснения: пользователь
  должен понимать, что `QUALIFIES` ребро не влияет на цвет узла
- (−) Если в будущем `QUALIFIES` всё-таки войдёт в алгоритм — это будет
  замена этого ADR (через новый ADR со статусом "заменяет ADR-007"),
  не уточнение

## ADR-008: React + TypeScript + Vite для фронтенда
**Дата:** 2026-05-03
**Статус:** принято
**Контекст:** нужно выбрать фреймворк для SPA-фронтенда argument map.
У разработчика нет опыта с JS-фреймворками — выбор должен оптимизировать
обучаемость, доступность ресурсов и совместимость с библиотеками
визуализации графа.

**Решение:** React 19 + TypeScript + Vite. Сборка через Vite, линтер
через ESLint, форматирование через Prettier. Типы — из `/v3/api-docs`
бэка через `openapi-typescript`.

**Причины:**
- Самая большая экосистема — любую проблему кто-то уже решил, готовые
  решения для роутинга, форм, состояния, тестирования
- Claude Code генерирует наиболее качественный код именно для React
  (больше всего обучающих данных)
- React Flow (см. ADR-009) работает только с React — это единственная
  жёсткая зависимость на фреймворк, и она очень критична для проекта
- TypeScript обязателен для синхронизации типов с бэкенд API
  (`api-contract.md` + OpenAPI генерация)
- Vite — стандарт для новых React-проектов, быстрый HMR, минимальная
  конфигурация, в отличие от Webpack/CRA

**Последствия:**
- (+) Максимум ресурсов, примеров, библиотек
- (+) Типобезопасность через TypeScript исключает целый класс ошибок
  на стыке с бэком
- (+) Нативная интеграция с React Flow без обёрток
- (−) JSX-синтаксис непривычен новичку — компенсируется тем, что
  Claude Code пишет основной объём кода
- (−) React сложнее чем Svelte/Vue для простых задач (нужно понимать
  хуки, ре-рендеры) — для нашего масштаба несущественно

## ADR-009: React Flow для визуализации графа
**Дата:** 2026-05-03
**Статус:** принято
**Контекст:** нужна библиотека для Miro-подобной визуализации графа
аргументов с drag-and-drop узлов, кастомизацией внешнего вида (цвета
по статусу, иконки по типу), отображением рёбер с подписями и стилями
по типу связи, автолейаутом и зум/пан.

**Решение:** React Flow (`@xyflow/react`).

**Причины:**
- Drag-and-drop узлов из коробки, как в Miro - центральный UX проекта
- Кастомные узлы через `nodeTypes`: карточки с цветом по статусу,
  контентом, весом - то, что нужно для отображения `Node` сущности
- Кастомные рёбра через `edgeTypes`: подписи (`SUPPORTS`/`REFUTES`/
  `INVALIDATES`/`QUALIFIES`/`RESPONDS_TO`), разные стили линий
  (пунктир для `INVALIDATES`)
- Формат данных `nodes[]` + `edges[]` совпадает с `GraphView`
  бэка (`api-contract.md`) — нулевая трансформация
- Мини-карта, зум, пан, автолейаут (через dagre/elkjs) из коробки
- Активно поддерживается, используется в Stripe, Typeform,
  Linear и других продакшн-приложениях

**Альтернативы рассмотрены:**
- **Cytoscape.js** — академический, визуально слабый, UX далёк от
  Miro, требует много кастомизации для drag-and-drop узлов
- **D3** — максимум контроля, но drag-and-drop, рёбра, лейаут с нуля =
  месяцы работы. Подходит для уникальной нестандартной визуализации,
  не для нашего use-case
- **vis.js** — устарел, слабая поддержка, сообщество фактически мертво

**Последствия:**
- (+) MVP визуализации за дни, не месяцы
- (+) Нативная интеграция с React (фрагментирует выбор фреймворка —
  но это уже зафиксировано в ADR-008)
- (+) Автолейаут через dagre для красивого расположения узлов
- (−) Жёсткая привязка к React (не портируется на Vue/Svelte) —
  принимаем как цену готового решения
- (−) Продвинутые фичи (группировка узлов, real-time collaboration)
  доступны только в React Flow Pro (платно). Для MVP не нужны;
  если когда-то понадобится — отдельный ADR

## ADR-010: Семантика типов связей и матрица допустимых пар
**Дата:** 2026-05-04
**Статус:** принято
**Контекст:** в системе 4 типа узлов (`QUESTION`, `CLAIM`, `ARGUMENT`,
`EVIDENCE`) и 5 типов рёбер (`SUPPORTS`, `REFUTES`, `INVALIDATES`,
`QUALIFIES`, `RESPONDS_TO`). На текущий момент любая комбинация
`(fromType, edgeType, toType)` допускалась - это породило бессмысленные
связи в реальных графах: например "вопрос опровергает тезис" или
"факт связывается с фактом". Нужны логические правила: какие пары
семантически валидны, а какие - бессмысленны.

**Решение:** ввести явную матрицу разрешённых пар
`(fromType, edgeType, toType)`. Связь, не вошедшая в матрицу, отклоняется
бэком (HTTP 422 `invalid-edge`) и фильтруется на фронте (тип ребра
просто не показывается в селекторе для данной пары узлов).

**Матрица:**

| FROM \ TO | QUESTION | CLAIM | ARGUMENT | EVIDENCE |
|---|---|---|---|---|
| **QUESTION** | QUALIFIES | QUALIFIES | QUALIFIES | — |
| **CLAIM** | RESPONDS_TO | SUPPORTS, REFUTES, QUALIFIES | — | — |
| **ARGUMENT** | — | SUPPORTS, REFUTES | INVALIDATES | — |
| **EVIDENCE** | — | SUPPORTS, REFUTES | SUPPORTS, REFUTES, INVALIDATES | — |

Прочерк = пара запрещена (любой `edgeType` отклоняется).

**Семантика по ролям типов узлов:**
- **QUESTION** - пассивный участник. Может только *уточнять*
  (`QUALIFIES`) другие узлы или *получать* ответ через `RESPONDS_TO`
- **CLAIM** - центральный участник. Связывается с другими CLAIM через
  `SUPPORTS`/`REFUTES`/`QUALIFIES`. Может быть ответом на QUESTION
- **ARGUMENT** - инструмент за/против тезиса: `SUPPORTS`/`REFUTES` →
  CLAIM. Может быть мета-опровергнут: `INVALIDATES` ← ARGUMENT/EVIDENCE
- **EVIDENCE** - доказательная база: `SUPPORTS`/`REFUTES` → CLAIM или
  ARGUMENT. Может быть основанием для `INVALIDATES`

**Запрещённые пары (примеры) и почему:**
- QUESTION → CLAIM (SUPPORTS/REFUTES) - вопрос не утверждает, он спрашивает
- CLAIM → ARGUMENT (любое) - аргументы порождаются, не порождают;
  ARGUMENT - инициатор, CLAIM - получатель
- EVIDENCE → EVIDENCE (любое) - факты не аргументируют факты, нужен
  ARGUMENT-посредник
- CLAIM → EVIDENCE - тезис не доказывает источник, направление обратное

**Контекстные подписи рёбер (UI):** одна edgeType-надпись для всех пар
непонятна на цепочках типа "поддерживает → поддерживает". Подпись
зависит от пары узлов:

| Edge | Контекст | Label |
|---|---|---|
| SUPPORTS | EVIDENCE → CLAIM/ARGUMENT | "доказывает" |
| SUPPORTS | ARGUMENT → CLAIM | "поддерживает" |
| SUPPORTS | CLAIM → CLAIM | "согласуется с" |
| REFUTES | EVIDENCE → CLAIM/ARGUMENT | "опровергает" |
| REFUTES | ARGUMENT → CLAIM | "противоречит" |
| REFUTES | CLAIM → CLAIM | "несовместим с" |
| INVALIDATES | EVIDENCE/ARGUMENT → ARGUMENT | "аннулирует" |
| QUALIFIES | QUESTION → * | "уточняет" |
| QUALIFIES | CLAIM → CLAIM | "сужает" |
| RESPONDS_TO | CLAIM → QUESTION | "отвечает на" |

**Причины:**
- Без правил граф вырождается в "что угодно → что угодно", теряет
  семантическую ценность как argument map
- Рассмотренные альтернативы:
  - Полностью свободный граф (текущее) - порождает мусор
  - Жёстко иерархическая модель (как Argunet, без CLAIM↔CLAIM) -
    неудобна для сравнения родственных тезисов
  - Правила только на UI без бэка - на API можно создать запрещённую
    пару напрямую, целостность данных не гарантирована
- Разрешение CLAIM↔CLAIM (с гайдлайном "по возможности через ARGUMENT
  для явности") - компромисс между гибкостью и формальностью
- Контекстные подписи решают проблему "поддерживает→поддерживает"
  без удаления текста с рёбер

**Последствия:**
- (+) Граф семантически чище, бессмысленные связи невозможны
- (+) UI помогает: при выборе пары узлов показываются только валидные
  типы связи, исключаем UX-friction
- (+) Бэк гарантирует целостность: даже прямой POST через curl не
  создаст бессмысленное ребро
- (−) Существующие графы могут содержать запрещённые пары - при
  внедрении нужна data-миграция (проверить что в БД, удалить либо
  пометить deprecated). Сейчас в БД мало данных - принимаем риск
- (−) Список разрешённых пар нужно поддерживать в двух местах
  (бэк-сервис + фронт-utility). Принимаем как цену типобезопасности
- (−) Если матрица в будущем расширится - это будет замена этого
  ADR (новый со статусом "заменяет ADR-010"), не уточнение

## ADR-011: Удаление поля `weight` до появления категориальной разметки
**Дата:** 2026-05-04
**Статус:** принято
**Контекст:** у узлов есть поле `weight: int 1-10`, заполняемое автором
при создании. Изначальная задумка - "сила убеждения / важность узла".
Проблема:
- Алгоритм `StatusCalculationService` фактически **не использует**
  weight - оперирует только структурой графа и статусами узлов
- На UI weight отображается как "10-точечная диаграмма + N/10",
  но не понятно что это значит. Каждая сторона аргумента
  естественно ставит максимум себе - метрика обесценивается
- Нет объективного способа задать weight: один автор оценивает
  свой довод 9, другой - тоже 9; сравнение невозможно
- Нет механизма пересмотра весов другими пользователями (для этого
  нужна авторизация - этап 6)

**Решение:** удалить поле `weight` из:
- БД (миграция drop column)
- доменной модели `Node`
- DTO `CreateNodeRequest`/`UpdateNodeRequest`/`NodeResponse`
- репозитория, сервиса, мапперов
- фронт-компонентов (`NodeCard`, `AddNodeModal`)
- тестов

В будущем (Stage 6 / после auth) вернуть подобную семантику в виде:
- **Категориальный маркер для ARGUMENT/EVIDENCE**: "факт",
  "мнение", "цитата", "статистика" и т.п. - объективная классификация,
  а не субъективное число
- **Voting** для накопительной оценки силы от сообщества
- **Reliability** для EVIDENCE расширить (сейчас только для HADITH:
  SAHIH/HASAN/DAIF) - сделать общим для любого типа источника

**Причины:**
- YAGNI: weight не используется алгоритмически, на UI вводит в
  заблуждение, защиты от максимизации нет → пустое поле, удалить
- Будущие категориальные маркеры (факт/мнение) более объективны и
  не страдают от проблемы "каждый ставит максимум"
- Удалить дешевле чем поддерживать неработающее поле
- Восстановление "потом" в новом виде - простое (добавить колонку,
  поле в DTO, UI-компонент) - дешевле чем сейчас "лечить" weight

**Последствия:**
- (+) Чище доменная модель: только то что реально работает
- (+) Никаких "ставлю 10 себе - значит мой довод сильнее" иллюзий
- (+) UI узла стал короче: иконка типа + контент + статус (без
  weight-bar)
- (−) Существующие данные (узлы в БД) теряют поле weight. Принимаем -
  данных мало, MVP-стадия
- (−) Когда вернётся категориальная разметка - это будет уже другая
  модель (категория вместо числа), требует нового UI и миграции.
  Принимаем: лучше сделать правильно потом, чем держать неправильное
  сейчас
- (−) Возможно у пользователей сложилось ожидание "у узла есть вес"
  из ER-диаграммы / старой документации - нужно явно зафиксировать
  изменение в `architecture.md`
