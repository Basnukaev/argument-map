# Архитектурные решения (ADR)

Записи о принятых решениях в формате ADR-lite (Architecture Decision Records).
Новые ADR — **снизу**, с возрастающим номером. Не переписывать старые —
если решение отменяется, добавлять новый ADR со статусом "отменяет ADR-N".

Формат:
```
## ADR-NNN: Краткое название
**Дата:** YYYY-MM-DD
**Статус:** принято | отменено | заменено ADR-X
**Контекст:** какая проблема решается
**Решение:** что решили делать
**Причины:** почему именно так
**Последствия:** что это влечёт (плюсы и минусы)
```

> **Примечание о порядке:** записи нумеруются по порядку принятия
> решения, но физически в файле могут идти не строго по возрастанию
> номера — ориентируйся на даты. Это нормально: ADR — исторический
> документ, порядок добавления = порядок принятия.

## ADR-001: JDBC Template вместо JPA/Hibernate
**Дата:** 2026-04-13
**Статус:** принято
**Контекст:** нужен слой доступа к БД для работы с графом аргументов

**Решение:** использовать Spring JDBC Template + ручные RowMapper'ы.
Не использовать JPA, Hibernate, Spring Data JPA.

**Причины:**
- Привычный стек для разработчика (как в проекте CREW)
- Полный контроль над генерируемым SQL — важно для графовых запросов
- Нет магии ленивой загрузки, N+1 проблем, кеша первого уровня
- Предсказуемое поведение транзакций
- Проще интеграционные тесты — меньше "магии"

**Последствия:**
- (+) Явный SQL, легко оптимизировать графовые обходы
- (+) Нет проблем с ленивой загрузкой рёбер/узлов
- (−) Больше бойлерплейта на CRUD — принимаем как цену

## ADR-002: Source и Authority — справочники, а не узлы графа
**Дата:** 2026-04-13
**Статус:** принято
**Контекст:** нужно решить, как хранить источники (хадисы, книги) и
мнения учёных — как узлы графа или отдельно

**Решение:** `sources` и `authorities` — отдельные таблицы-справочники.
Связь с узлами — через M:N таблицы `node_sources` и `node_authorities`
с дополнительными метаданными (цитата, контекст, позиция).

**Причины:**
- Один хадис может цитироваться в десятках тем — не хотим дублирования
- У учёного есть свой профиль (эпоха, мазхаб, биография) — это не "аргумент"
- Источники и авторитеты должны искаться независимо от конкретных тем
- Справочники переиспользуются между пользователями и темами

**Последствия:**
- (+) Нет дублирования данных об источниках и учёных
- (+) Возможен независимый поиск/фильтрация по справочникам
- (+) Можно строить статистику "на какие хадисы чаще ссылаются"
- (−) Отдельная логика для привязки источников к узлам (M:N таблицы)

## ADR-003: Граф в двух таблицах (nodes + edges) с дискриминатором
**Дата:** 2026-04-13
**Статус:** принято
**Контекст:** нужно выбрать способ хранения графа в PostgreSQL

**Решение:** две таблицы — `nodes` (все узлы любого типа) и `edges` (все рёбра
любого типа). Тип различается через колонку-дискриминатор (`node_type`,
`edge_type`). Не создавать отдельные таблицы под каждый тип узла/ребра.

**Причины:**
- Гибкость: новый тип узла или связи добавляется без миграции схемы
- Простота графовых запросов: один JOIN вместо UNION по нескольким таблицам
- Количество типов небольшое и стабильное (4-5 типов узлов, 5 типов рёбер)
- Поля у всех типов узлов почти одинаковые (`content`, `status`, `weight`)

**Последствия:**
- (+) Простая схема, простые запросы
- (+) Легко добавлять новые типы узлов и связей
- (−) Нельзя делать тип-специфичные NOT NULL constraints на уровне БД —
  валидация в сервисном слое
- (−) Если у какого-то типа узла появится много специфичных полей — придётся
  использовать `jsonb` колонку или выделять в отдельную таблицу

## ADR-004: Maven вместо Gradle
**Дата:** 2026-04-13
**Статус:** принято
**Контекст:** нужно выбрать систему сборки для Java/Spring Boot бэкенда

**Решение:** использовать Maven (с Maven Wrapper). Не использовать Gradle.

**Причины:**
- Привычный стек для разработчика (аналогичная конфигурация в проекте CREW)
- Декларативный `pom.xml` проще для чтения и поддержки в проекте
  без сложной кастомизации сборки
- Максимальная совместимость с экосистемой Spring Boot — примеры,
  документация, плагины в первую очередь поддерживают Maven
- Maven Wrapper (`mvnw`) обеспечивает воспроизводимую сборку без
  глобальной установки Maven

**Последствия:**
- (+) Меньше порог входа — стандартный XML-конфиг без Groovy/Kotlin DSL
- (+) Предсказуемое поведение без "магии" Gradle-кеша
- (−) XML-конфигурация более многословна, чем Gradle DSL
- (−) Инкрементальная сборка медленнее чем у Gradle — для нашего
  размера проекта несущественно

## ADR-005: Монорепа с независимыми backend/ и frontend/
**Дата:** 2026-04-13
**Статус:** принято
**Контекст:** проект состоит из двух технологически разных частей —
Java/Spring-бэкенд и будущий JS/TS-фронтенд. Нужно решить, хранить их
в одном репозитории или в разных.

**Решение:** монорепа с двумя независимыми подпапками — `backend/` и
`frontend/`. Без специализированных инструментов монорепы (Nx, Turborepo,
Bazel). Каждая часть имеет свой build-инструмент, свои зависимости, свои
тесты. Общая документация продукта — в корневом `docs/`. Технологически
специфичная — в `backend/docs/` и `frontend/docs/`.

**Причины:**
- Одна история изменений — удобно отслеживать совместные изменения
  (например, новый эндпоинт + клиент для него в одном PR)
- Общие решения (архитектура, термины, ADR) живут в одном месте
- Инфраструктура (`docker-compose.yml`) общая — Postgres нужен и беку
  для работы, и фронту для e2e-тестов
- Специализированные инструменты монорепы — оверкилл для двух подпроектов
  на разных языках без shared-кода
- Простая модель: каждая часть независима, можно работать над одной, не
  трогая другую

**Последствия:**
- (+) Один `git clone`, один PR на сквозные изменения
- (+) Общая документация видна обеим частям
- (+) Нет сложности настройки (никаких workspace-конфигов, lerna, nx.json)
- (−) CI должен уметь собирать обе части, детектируя изменённые пути
- (−) Claude Code нужно запускать внутри конкретной подпапки
  (`cd backend && claude`), не в корне — это описано в `README.md`
- (−) При росте проекта возможно потребуется миграция на инструменты
  монорепы — принимаем как цену простоты на старте

## ADR-006: `createdBy` через HTTP-заголовок `X-User-Id` до появления авторизации
**Дата:** 2026-05-03
**Статус:** принято
**Контекст:** колонки `created_by` во всех таблицах уже `NOT NULL` (Этап 1
закрыт), но полноценная авторизация (Spring Security, JWT) запланирована
только на Этап 6. На Этапе 3 нужно начать писать сервисный слой с
операциями мутации (`createTopic`, `createNode`, `createEdge`,
`createRevision`), и каждой из них требуется UUID автора. Откуда брать
этот UUID сейчас?

**Решение:** контроллеры читают `X-User-Id` (UUID) из HTTP-заголовка,
валидируют существование такого пользователя в таблице `users` и
прокидывают `UUID userId` явным параметром в методы сервисов, требующие
авторства. Сервисы не знают про HTTP-контекст. Тесты сервисного слоя
получают `userId` напрямую как аргумент. Для интеграционных и e2e-сценариев
пользователь в `users` создаётся фикстурой / отдельной seed-миграцией.

**Причины:**
- Минимальная заглушка под будущий Spring Security: при его появлении
  поменяется только источник UUID — контроллер достаёт его из
  `Authentication`/`Principal` вместо заголовка, контракты сервисов
  не меняются. Никакого `Optional<UUID>`, никаких "system user" хардкодов
- Не пускаем `createdBy` в тело запроса (антипаттерн — клиент сможет
  писать от чужого имени; при появлении авторизации придётся ломать API)
- Не плодим "одного системного пользователя" — терялась бы реальная
  история авторства, при апгрейде до multiuser пришлось бы делать
  data-миграцию с разделением
- Не делаем ленивую регистрацию по `username` — вне цели MVP, плодит
  состояние, которое потом сложно ломать

**Последствия:**
- (+) API сервисов финальный — при подключении Security сигнатуры не
  меняются
- (+) Тесты сервисов остаются простыми: `userId` — обычный параметр
- (+) Можно тестировать multiuser-сценарии (несколько `X-User-Id`) уже
  на Этапе 3
- (+) Контроллеры получают чёткую обязанность: распарсить заголовок,
  валидировать пользователя, прокинуть UUID. Это естественная граница
  под будущий `@AuthenticationPrincipal`
- (−) Контроллер делает один лишний запрос к `users` для валидации
  (можно кешировать, но для MVP не нужно)
- (−) Любой клиент, знающий чужой UUID, пишет от его имени. Принимаем
  как временный риск — это **не** прод-механизм, должен быть закрыт
  на Этапе 6 одновременно с появлением Spring Security
- (−) Заголовок `X-User-Id` нужно явно прописать в `api-contract.md`
  как требуемый для всех мутирующих эндпоинтов

## ADR-007: Вклад типов рёбер в алгоритм пересчёта статусов
**Дата:** 2026-05-03
**Статус:** принято
**Контекст:** в проекте 5 типов рёбер (`SUPPORTS`, `REFUTES`,
`QUALIFIES`, `INVALIDATES`, `RESPONDS_TO`), а MVP-алгоритм пересчёта
статусов в `architecture.md` описан в терминах "supports" / "refutes".
Нужно зафиксировать вклад каждого типа, иначе сервис `StatusCalculation`
будет неполным/неоднозначным.

**Решение:**

| Тип ребра | Вклад в статус |
|---|---|
| `SUPPORTS` | поддержка |
| `REFUTES` | опровержение |
| `INVALIDATES` | "жёсткий kill": если источник `STANDING`, цель → `REFUTED` безусловно (бьёт даже стену `STANDING` supports) |
| `QUALIFIES` | не влияет на статус (только семантика "уточняет применимость") |
| `RESPONDS_TO` | не влияет на статус (организационная связь "это ответ на это") |

**Причины:**
- Соответствует языку `architecture.md`: "INVALIDATES действует на ребро
  или узел как 'жёсткое' опровержение, сильнее чем REFUTES"
- `QUALIFIES` ≠ `REFUTES` семантически: уточнение области применения
  тезиса не делает его ложным, поэтому в MVP не вмешиваем в алгоритм
- `RESPONDS_TO` — диалоговая структура ("это реплика-ответ на эту
  реплику"), не оценочная связь. На вопрос можно "ответить" разными
  способами, в том числе сомнениями
- `INVALIDATES` как kill-switch (а не просто "сильный refute") даёт
  однозначную семантику для мета-аргументов из изначального примера в
  `architecture.md` ("сказанное в противовес учёному нерелевантно")
- KISS: `QUALIFIES` и `RESPONDS_TO` остаются "значимыми, но не
  алгоритмическими" — их можно повысить до influencing-типов с весами
  без миграции схемы, когда появится продвинутая версия алгоритма (Dung)

**Последствия:**
- (+) Алгоритм пересчёта компактен: учитывает только 3 типа из 5
- (+) `QUALIFIES`/`RESPONDS_TO` остаются полноценными гражданами графа
  (показываются на UI, попадают в `GET /graph`), но не вызывают
  каскадных пересчётов
- (+) Семантика `INVALIDATES` отделена от обычного `REFUTES` — это
  отражает реальное мета-уровневое использование
- (−) `QUALIFIES`-связи требуют отдельного UI-объяснения: пользователь
  должен понимать, что `QUALIFIES` ребро не влияет на цвет узла
- (−) Если в будущем `QUALIFIES` всё-таки войдёт в алгоритм — это будет
  замена этого ADR (через новый ADR со статусом "заменяет ADR-007"),
  не уточнение

## ADR-008: React + TypeScript + Vite для фронтенда
**Дата:** 2026-05-03
**Статус:** принято
**Контекст:** нужно выбрать фреймворк для SPA-фронтенда argument map.
У разработчика нет опыта с JS-фреймворками — выбор должен оптимизировать
обучаемость, доступность ресурсов и совместимость с библиотеками
визуализации графа.

**Решение:** React 19 + TypeScript + Vite. Сборка через Vite, линтер
через ESLint, форматирование через Prettier. Типы — из `/v3/api-docs`
бэка через `openapi-typescript`.

**Причины:**
- Самая большая экосистема — любую проблему кто-то уже решил, готовые
  решения для роутинга, форм, состояния, тестирования
- Claude Code генерирует наиболее качественный код именно для React
  (больше всего обучающих данных)
- React Flow (см. ADR-009) работает только с React — это единственная
  жёсткая зависимость на фреймворк, и она очень критична для проекта
- TypeScript обязателен для синхронизации типов с бэкенд API
  (`api-contract.md` + OpenAPI генерация)
- Vite — стандарт для новых React-проектов, быстрый HMR, минимальная
  конфигурация, в отличие от Webpack/CRA

**Последствия:**
- (+) Максимум ресурсов, примеров, библиотек
- (+) Типобезопасность через TypeScript исключает целый класс ошибок
  на стыке с бэком
- (+) Нативная интеграция с React Flow без обёрток
- (−) JSX-синтаксис непривычен новичку — компенсируется тем, что
  Claude Code пишет основной объём кода
- (−) React сложнее чем Svelte/Vue для простых задач (нужно понимать
  хуки, ре-рендеры) — для нашего масштаба несущественно

## ADR-009: React Flow для визуализации графа
**Дата:** 2026-05-03
**Статус:** принято
**Контекст:** нужна библиотека для Miro-подобной визуализации графа
аргументов с drag-and-drop узлов, кастомизацией внешнего вида (цвета
по статусу, иконки по типу), отображением рёбер с подписями и стилями
по типу связи, автолейаутом и зум/пан.

**Решение:** React Flow (`@xyflow/react`).

**Причины:**
- Drag-and-drop узлов из коробки, как в Miro - центральный UX проекта
- Кастомные узлы через `nodeTypes`: карточки с цветом по статусу,
  контентом, весом - то, что нужно для отображения `Node` сущности
- Кастомные рёбра через `edgeTypes`: подписи (`SUPPORTS`/`REFUTES`/
  `INVALIDATES`/`QUALIFIES`/`RESPONDS_TO`), разные стили линий
  (пунктир для `INVALIDATES`)
- Формат данных `nodes[]` + `edges[]` совпадает с `GraphView`
  бэка (`api-contract.md`) — нулевая трансформация
- Мини-карта, зум, пан, автолейаут (через dagre/elkjs) из коробки
- Активно поддерживается, используется в Stripe, Typeform,
  Linear и других продакшн-приложениях

**Альтернативы рассмотрены:**
- **Cytoscape.js** — академический, визуально слабый, UX далёк от
  Miro, требует много кастомизации для drag-and-drop узлов
- **D3** — максимум контроля, но drag-and-drop, рёбра, лейаут с нуля =
  месяцы работы. Подходит для уникальной нестандартной визуализации,
  не для нашего use-case
- **vis.js** — устарел, слабая поддержка, сообщество фактически мертво

**Последствия:**
- (+) MVP визуализации за дни, не месяцы
- (+) Нативная интеграция с React (фрагментирует выбор фреймворка —
  но это уже зафиксировано в ADR-008)
- (+) Автолейаут через dagre для красивого расположения узлов
- (−) Жёсткая привязка к React (не портируется на Vue/Svelte) —
  принимаем как цену готового решения
- (−) Продвинутые фичи (группировка узлов, real-time collaboration)
  доступны только в React Flow Pro (платно). Для MVP не нужны;
  если когда-то понадобится — отдельный ADR

## ADR-010: Семантика типов связей и матрица допустимых пар
**Дата:** 2026-05-04
**Статус:** принято
**Контекст:** в системе 4 типа узлов (`QUESTION`, `CLAIM`, `ARGUMENT`,
`EVIDENCE`) и 5 типов рёбер (`SUPPORTS`, `REFUTES`, `INVALIDATES`,
`QUALIFIES`, `RESPONDS_TO`). На текущий момент любая комбинация
`(fromType, edgeType, toType)` допускалась - это породило бессмысленные
связи в реальных графах: например "вопрос опровергает тезис" или
"факт связывается с фактом". Нужны логические правила: какие пары
семантически валидны, а какие - бессмысленны.

**Решение:** ввести явную матрицу разрешённых пар
`(fromType, edgeType, toType)`. Связь, не вошедшая в матрицу, отклоняется
бэком (HTTP 422 `invalid-edge`) и фильтруется на фронте (тип ребра
просто не показывается в селекторе для данной пары узлов).

**Матрица:**

| FROM \ TO | QUESTION | CLAIM | ARGUMENT | EVIDENCE |
|---|---|---|---|---|
| **QUESTION** | QUALIFIES | QUALIFIES | QUALIFIES | — |
| **CLAIM** | RESPONDS_TO | SUPPORTS, REFUTES, QUALIFIES | — | — |
| **ARGUMENT** | — | SUPPORTS, REFUTES | INVALIDATES | — |
| **EVIDENCE** | — | SUPPORTS, REFUTES | SUPPORTS, REFUTES, INVALIDATES | — |

Прочерк = пара запрещена (любой `edgeType` отклоняется).

**Семантика по ролям типов узлов:**
- **QUESTION** - пассивный участник. Может только *уточнять*
  (`QUALIFIES`) другие узлы или *получать* ответ через `RESPONDS_TO`
- **CLAIM** - центральный участник. Связывается с другими CLAIM через
  `SUPPORTS`/`REFUTES`/`QUALIFIES`. Может быть ответом на QUESTION
- **ARGUMENT** - инструмент за/против тезиса: `SUPPORTS`/`REFUTES` →
  CLAIM. Может быть мета-опровергнут: `INVALIDATES` ← ARGUMENT/EVIDENCE
- **EVIDENCE** - доказательная база: `SUPPORTS`/`REFUTES` → CLAIM или
  ARGUMENT. Может быть основанием для `INVALIDATES`

**Запрещённые пары (примеры) и почему:**
- QUESTION → CLAIM (SUPPORTS/REFUTES) - вопрос не утверждает, он спрашивает
- CLAIM → ARGUMENT (любое) - аргументы порождаются, не порождают;
  ARGUMENT - инициатор, CLAIM - получатель
- EVIDENCE → EVIDENCE (любое) - факты не аргументируют факты, нужен
  ARGUMENT-посредник
- CLAIM → EVIDENCE - тезис не доказывает источник, направление обратное

**Контекстные подписи рёбер (UI):** одна edgeType-надпись для всех пар
непонятна на цепочках типа "поддерживает → поддерживает". Подпись
зависит от пары узлов:

| Edge | Контекст | Label |
|---|---|---|
| SUPPORTS | EVIDENCE → CLAIM/ARGUMENT | "доказывает" |
| SUPPORTS | ARGUMENT → CLAIM | "поддерживает" |
| SUPPORTS | CLAIM → CLAIM | "согласуется с" |
| REFUTES | EVIDENCE → CLAIM/ARGUMENT | "опровергает" |
| REFUTES | ARGUMENT → CLAIM | "противоречит" |
| REFUTES | CLAIM → CLAIM | "несовместим с" |
| INVALIDATES | EVIDENCE/ARGUMENT → ARGUMENT | "аннулирует" |
| QUALIFIES | QUESTION → * | "уточняет" |
| QUALIFIES | CLAIM → CLAIM | "сужает" |
| RESPONDS_TO | CLAIM → QUESTION | "отвечает на" |

**Причины:**
- Без правил граф вырождается в "что угодно → что угодно", теряет
  семантическую ценность как argument map
- Рассмотренные альтернативы:
  - Полностью свободный граф (текущее) - порождает мусор
  - Жёстко иерархическая модель (как Argunet, без CLAIM↔CLAIM) -
    неудобна для сравнения родственных тезисов
  - Правила только на UI без бэка - на API можно создать запрещённую
    пару напрямую, целостность данных не гарантирована
- Разрешение CLAIM↔CLAIM (с гайдлайном "по возможности через ARGUMENT
  для явности") - компромисс между гибкостью и формальностью
- Контекстные подписи решают проблему "поддерживает→поддерживает"
  без удаления текста с рёбер

**Последствия:**
- (+) Граф семантически чище, бессмысленные связи невозможны
- (+) UI помогает: при выборе пары узлов показываются только валидные
  типы связи, исключаем UX-friction
- (+) Бэк гарантирует целостность: даже прямой POST через curl не
  создаст бессмысленное ребро
- (−) Существующие графы могут содержать запрещённые пары - при
  внедрении нужна data-миграция (проверить что в БД, удалить либо
  пометить deprecated). Сейчас в БД мало данных - принимаем риск
- (−) Список разрешённых пар нужно поддерживать в двух местах
  (бэк-сервис + фронт-utility). Принимаем как цену типобезопасности
- (−) Если матрица в будущем расширится - это будет замена этого
  ADR (новый со статусом "заменяет ADR-010"), не уточнение

## ADR-011: Удаление поля `weight` до появления категориальной разметки
**Дата:** 2026-05-04
**Статус:** принято
**Контекст:** у узлов есть поле `weight: int 1-10`, заполняемое автором
при создании. Изначальная задумка - "сила убеждения / важность узла".
Проблема:
- Алгоритм `StatusCalculationService` фактически **не использует**
  weight - оперирует только структурой графа и статусами узлов
- На UI weight отображается как "10-точечная диаграмма + N/10",
  но не понятно что это значит. Каждая сторона аргумента
  естественно ставит максимум себе - метрика обесценивается
- Нет объективного способа задать weight: один автор оценивает
  свой довод 9, другой - тоже 9; сравнение невозможно
- Нет механизма пересмотра весов другими пользователями (для этого
  нужна авторизация - этап 6)

**Решение:** удалить поле `weight` из:
- БД (миграция drop column)
- доменной модели `Node`
- DTO `CreateNodeRequest`/`UpdateNodeRequest`/`NodeResponse`
- репозитория, сервиса, мапперов
- фронт-компонентов (`NodeCard`, `AddNodeModal`)
- тестов

В будущем (Stage 6 / после auth) вернуть подобную семантику в виде:
- **Категориальный маркер для ARGUMENT/EVIDENCE**: "факт",
  "мнение", "цитата", "статистика" и т.п. - объективная классификация,
  а не субъективное число
- **Voting** для накопительной оценки силы от сообщества
- **Reliability** для EVIDENCE расширить (сейчас только для HADITH:
  SAHIH/HASAN/DAIF) - сделать общим для любого типа источника

**Причины:**
- YAGNI: weight не используется алгоритмически, на UI вводит в
  заблуждение, защиты от максимизации нет → пустое поле, удалить
- Будущие категориальные маркеры (факт/мнение) более объективны и
  не страдают от проблемы "каждый ставит максимум"
- Удалить дешевле чем поддерживать неработающее поле
- Восстановление "потом" в новом виде - простое (добавить колонку,
  поле в DTO, UI-компонент) - дешевле чем сейчас "лечить" weight

**Последствия:**
- (+) Чище доменная модель: только то что реально работает
- (+) Никаких "ставлю 10 себе - значит мой довод сильнее" иллюзий
- (+) UI узла стал короче: иконка типа + контент + статус (без
  weight-bar)
- (−) Существующие данные (узлы в БД) теряют поле weight. Принимаем -
  данных мало, MVP-стадия
- (−) Когда вернётся категориальная разметка - это будет уже другая
  модель (категория вместо числа), требует нового UI и миграции.
  Принимаем: лучше сделать правильно потом, чем держать неправильное
  сейчас
- (−) Возможно у пользователей сложилось ожидание "у узла есть вес"
  из ER-диаграммы / старой документации - нужно явно зафиксировать
  изменение в `architecture.md`

## ADR-012: Координаты узла на канвасе как часть `Node`, расширение PATCH
**Дата:** 2026-05-05
**Статус:** принято
**Контекст:** на этапе 9 (Miro UX) пользователь перетаскивает узлы по
канвасу. После refetch графа dagre заново вычислял позиции и
ручной layout пользователя терялся. Нужен персистентный layout: фронт
должен сохранять позиции, бэк хранить, при перезагрузке возвращать.

Альтернативы рассмотрены:
1. **localStorage на фронте** - не работает кросс-сессионно/кросс-устройств,
   у других пользователей будут чужие позиции по тому же ID темы
2. **Отдельный эндпоинт `PATCH /api/v1/nodes/{id}/position`** - чистая
   семантическая граница (revision-обновления отдельно от
   layout-обновлений), но плодит API surface для одной таблицы
3. **Расширение существующего `PATCH /api/v1/nodes/{id}`** opt-полями
   `posX`/`posY` - один универсальный endpoint, фронту проще
   (один `apiPatchRaw` вместо двух)
4. **Отдельная таблица `node_positions`** (M:N с user_id для
   персональных layout'ов) - оверкилл для MVP, нет requirement'а на
   персональные layout'ы

**Решение:**
1. Добавить в таблицу `nodes` колонки `pos_x`, `pos_y` типа
   `DOUBLE PRECISION NULL` (миграция 13). Nullable - старые узлы
   получают `null`, фронт применяет автолейаут (dagre)
2. Расширить доменную модель `Node` полями `Double posX`, `Double posY`
3. `UpdateNodeRequest` принимает opt `content` и/или opt `posX`+`posY`:
   - только `content` → `updateContent` (revision + новый updatedAt
     как раньше)
   - только `posX+posY` → `updatePosition` (без revision, без
     изменения updatedAt - позиция != содержимое)
   - оба → последовательно, response = финальное состояние
   - ничего → 400 `illegal-argument`
4. `NodeResponse` расширен `posX`/`posY`
5. Фронт `onNodeDragStop` оптимистично PATCH'ит координаты, при ошибке
   - `toast.error`. `layoutGraph` уважает сохранённые координаты:
   режим "all-or-nothing" заменён на смешанный (saved as-is +
   fresh столбцом справа)

**Причины:**
- Универсальный PATCH меньше API surface чем отдельный
  `/position` эндпоинт. Фронту не нужно различать "обновить контент"
  и "обновить позицию" - один путь, один helper
- Семантическая ассимметрия (revision только для content) - явная и
  валидируется в `NodeService.updatePosition` (без записи Revision,
  без обновления updatedAt). Это **нормально**: позиция не часть
  истории контента, у неё нет аудита
- DOUBLE PRECISION (а не INT) - drag даёт дробные пиксели, округление
  было бы потеряно
- Nullable колонки вместо DEFAULT 0 - явно отличаем "ещё не drag'али"
  от "поставили в (0,0)"
- Координаты в `Node`, не в отдельной таблице - сейчас layout общий
  для всех пользователей (как в коллаборативных Miro/Figma на shared
  доске). Если потребуется персональный layout - отдельный ADR с
  таблицей `node_positions(node_id, user_id, pos_x, pos_y)`

**Последствия:**
- (+) Один универсальный PATCH вместо двух эндпоинтов
- (+) Layout сохраняется между сессиями и устройствами
- (+) При переходе к коллаборации (если будет) общий layout - это
  естественное поведение (видишь чужие drag'и)
- (+) Расширение поведенческое, не ломающее: старые клиенты
  по-прежнему могут слать PATCH с одним `content`
- (−) Nullable poseX/posY проникают в доменную модель `Node` - не все
  узлы их имеют. Везде где конструируется `Node` - проставляется
  `null/null` (TopicService, NodeService.createNode, тесты)
- (−) Фронту нужен `layoutGraph` mixed-режим (saved as-is + fresh
  столбцом). Для совсем нового графа dagre всё ещё работает
- (−) Если потребуется персональный layout (per-user) - нужен новый
  ADR с миграцией данных в `node_positions` (или сделать `pos_x`/
  `pos_y` deprecated и вторую таблицу)
- (−) Возможно конкурентные drag'и одного узла разными пользователями
  будут перезаписывать друг друга (last-write-wins). На MVP принимаем,
  при появлении коллаборации добавим CRDT/operational transform или
  optimistic locking

## ADR-013: `sourceHandle`/`targetHandle` как часть `Edge`
**Дата:** 2026-05-05
**Статус:** принято
**Контекст:** этап 9 добавил 4 handle'а на узле (top/right/bottom/left).
При drag-create в React Flow пользователь явно выбирает конкретные
стороны: тянет от "right" одного узла к "left" другого. После
сохранения ребра и refetch графа эта информация терялась - бэк
хранил только `from_node_id`/`to_node_id`. RF при рендере без
`sourceHandle`/`targetHandle` использует auto-routing, выбирая стороны
по позициям узлов. Симптом: пользователь нарисовал ребро через
конкретные точки, перезагрузил - стороны выбраны другие.

Альтернативы рассмотрены:
1. **localStorage на фронте** - не работает кросс-сессионно/устройств,
   те же проблемы что у позиций (см. ADR-012)
2. **Хранить только локально, не персистить** - тогда нет смысла в 4
   handles, после первого refetch всё равно auto-routing
3. **Отдельная таблица `edge_handles(edge_id, source_handle,
   target_handle)`** - оверкилл, поля 1:1 с edge, нет независимой
   жизни
4. **Расширение `edges` колонками `source_handle`/`target_handle`
   `VARCHAR(20) NULL`** - аналогично ADR-012 для узлов

**Решение:** идти по пути ADR-012:
1. Миграция 14 добавляет в `edges` две nullable колонки
   `source_handle`/`target_handle` типа `VARCHAR(20)`. Nullable -
   старые рёбра без сохранённых сторон при загрузке используют
   RF auto-routing как раньше
2. Доменный `Edge` record расширяется полями `String sourceHandle`,
   `String targetHandle`
3. `CreateEdgeRequest` принимает opt `sourceHandle`/`targetHandle`,
   `EdgeService.createEdge` имеет два варианта: с handle и без
   (overload). Без handle - для bulk-импорта и тестовых фикстур
   где сторона не важна
4. `EdgeResponse` расширен `sourceHandle`/`targetHandle`
5. Фронт `onConnect` передаёт `connection.sourceHandle`/`targetHandle`
   из RF в `POST /edges`. `CustomEdge` через `data` получает их и
   передаёт в `Handle`-ссылающиеся пропсы RF

**Причины:**
- Полная аналогия с ADR-012 - тот же подход для тех же причин
  (кросс-сессионность, единый универсальный API)
- VARCHAR(20) запас на возможные будущие handle id; сейчас "top",
  "right", "bottom", "left" максимум 6 символов
- Nullable вместо DEFAULT - явно отличаем "ребро создано не через
  drag" от "drag из конкретной точки"
- Overload `createEdge` без handle - чтобы не модифицировать все
  существующие IT и сервисы, где handle не важен

**Последствия:**
- (+) После refetch ребро рисуется именно из того handle'а откуда
  пользователь его тянул
- (+) Расширение поведенческое: старые клиенты могут не передавать
  handle - получится auto-routing как раньше
- (+) Параллельно с posX/posY (ADR-012) даёт полностью
  персистентный layout: позиции + стороны рёбер
- (−) Дополнительные две колонки в `edges`. На MVP объёме данных
  несущественно
- (−) `Edge` record растёт до 9 полей. Везде где конструируется
  `new Edge(...)` - расширяется null-параметрами или вызывается
  новый overload

## ADR-014: Reconnect рёбер через универсальный `PATCH /api/v1/edges/{id}`
**Дата:** 2026-05-05
**Статус:** принято
**Контекст:** на этапе 9 был добавлен drag-create рёбер, но обратная
операция - reconnect (перетащить конец существующего ребра на другой
handle/узел) - не была реализована. React Flow предоставляет хук
`onReconnect`, который вызывается при перетаскивании конца ребра. На
бэке нет endpoint для модификации существующего ребра - только
`POST` (создать) и `DELETE` (удалить).

Альтернативы рассмотрены:
1. **DELETE + POST на фронте в `onReconnect`** - 20 минут работы, без
   бэк-изменений. Минусы:
   - id ребра меняется (новый UUID после POST), ломаются ссылки
     если где-то держим edgeId
   - теоретическая гонка между DELETE и POST: если DELETE прошёл,
     а POST упал (валидация / сеть) - старое ребро уже удалено
   - две сетевые операции на один пользовательский жест - флакер
     при медленной сети
2. **Sub-resource `PATCH /api/v1/edges/{id}/reconnect`** - именная
   семантика "только reconnect". Минусы: один use-case → один
   endpoint - плодит API surface. Если потом понадобится менять
   rationale/edgeType - снова новый endpoint
3. **Полная замена через `PUT /api/v1/edges/{id}`** - REST-классика.
   Минусы: PUT требует все поля в body, а пользователь меняет только
   handle - фронт обязан собрать полный объект из текущего
   состояния. Громоздко
4. **Универсальный `PATCH /api/v1/edges/{id}`** с partial body -
   передаются только меняющиеся поля, остальные сохраняются. Финальное
   состояние валидируется целиком. Параллель с ADR-012 (PATCH
   `/nodes/{id}` для content/position)

**Решение:** идти по пути 4 - расширить EdgeController новым PATCH
endpoint с partial UpdateEdgeRequest. Все поля опциональные:
`fromNodeId`, `toNodeId`, `edgeType`, `rationale`, `sourceHandle`,
`targetHandle`. EdgeService.updateEdge мерджит передаваемые поля с
существующим состоянием, прогоняет полную валидацию (selfloop, граница
темы, матрица ADR-010), сохраняет в БД одним UPDATE. Если валидация
упала - InvalidEdgeException и `@Transactional` откатывает транзакцию,
ребро остаётся в исходном виде.

Если изменился структурный блок (`fromNode`/`toNode`/`edgeType`) -
пересчёт статусов темы. Если только `rationale`/`sourceHandle`/
`targetHandle` - пересчёт не нужен (на алгоритм не влияют, сэкономим).

Ограничение MVP: через PATCH нельзя "очистить" опциональные строковые
поля (выставить null) - null трактуется как "не передано". Для очистки
потребуется отдельный feature (sentinel-значение или JsonNullable).
Для reconnect это не нужно - handle всегда передаётся новый, не
обнуляется.

**Причины:**
- DELETE+POST ломает id и создаёт гонку - неприемлемо для core UX
- Один универсальный PATCH решает не только reconnect, но и любые
  будущие edits ребра (rationale, type) одним endpoint'ом
- Параллель с ADR-012 (PATCH nodes) - пользователь и фронт работают
  единообразно: "PATCH с тем что меняется"
- Атомарность через `@Transactional`: либо ребро применилось целиком,
  либо не изменилось вовсе. Никаких частичных состояний

**Последствия:**
- (+) Reconnect через одну сетевую операцию, id ребра сохраняется
- (+) Можно расширять PATCH новыми полями без новых endpoint'ов
- (+) Симметрия с PATCH nodes (ADR-012) - один паттерн на проект
- (+) `@Transactional` гарантирует "всё-или-ничего" - даже если
  валидация ADR-010 упала на финальном состоянии, БД не тронута
- (−) Пустой body (все поля null) приводит к 400. Это сознательная
  валидация в контроллере: PATCH без полей бессмыслен. Симметрично
  PATCH nodes (там тоже 400 при пустом)
- (−) "Очистить rationale" через PATCH невозможно - принимаем как
  цену простоты на MVP. Если потребуется - отдельный feature
- (−) Repeated валидация на каждом PATCH - даже если меняется только
  `rationale`, прогоняется полная цепочка проверок. Стоит дешёво:
  один SELECT + матричная проверка

## ADR-015: Статус узла как полоса 5px слева вместо `border-2` вокруг карточки

**Дата:** 2026-05-07
**Статус:** принято
**Контекст:** В `NodeCard` цвет статуса (`STANDING`/`DISPUTED`/
`REFUTED`/`UNVERIFIED`) был выражен через `border-2 border-{c}-500
bg-{c}-50` - вся карточка обведена цветной рамкой, заливка
полупрозрачная. При работе над визуальной полировкой по
`design-reference/` обнаружено: такой подход
(а) "конкурирует" с цветом типа узла (тип хочет тоже занять видную
часть header) - оба сигнала борются за внимание;
(б) занимает контур карточки, лишая возможности использовать
border/ring для других сигналов (selected/hover);
(в) заливка светло-цветным фоном делает текст менее читабельным
для DISPUTED (амбер) и REFUTED (красный) на длинных карточках.

В дизайн-референсе вместо этого:
- Цветная полоса `5px` слева у карточки (`bg-{c}-500
  rounded-l-xl`)
- Сам контур карточки белый (`bg-white`) с нейтральным
  `border-slate-200`
- Тип узла - в капсуле (`TypeChip`) в header
- Selected - `border-indigo-500` + ring (контур свободен)

**Решение:** перейти на status-bar слева. Кардинально:
- Удаление `border-2 border-{c}-500 bg-{c}-50` из NodeCard
- Добавление `<div className="absolute left-0 top-0 bottom-0
  w-[5px] rounded-l-xl bg-{c}-500" />` внутри карточки
- Контур карточки: нейтральный `border-slate-200`
- Selected: `border-indigo-500 + ring + усиленная тень`
- Hover: `shadow-md + border-slate-300` (свободный контур)

Цветовые токены статуса в `designTokens.ts` сохранены - переиспользуются
в `StatusBadge` (бэйдж в header карточки) и `NodeDetailsPanel` (header
с градиентом). То есть цвет статуса не исчезает, он перераспределяется
между bar+badge.

**Альтернативы:**
1. **Оставить border-2 как есть** - наименьшее изменение. Минусы
   описаны в контексте: тип и статус конкурируют, контур занят
2. **Border-left only (`border-l-4`)** - близкий компромисс.
   Минусы: visual мягче, но `border-l-4` влияет на padding и не
   так чётко видно как абсолютный bar. Также нельзя сочетать
   с `border-indigo-500` для selected (border-l будет цветной от
   статуса, остальные стороны от selected - три цвета границы)
3. **Status-bar слева 5px** (выбрано) - чистое разделение
   сигналов: статус → bar, тип → chip, selected → border+ring.
   Каждый канал коммуникации имеет свою область
4. **Цветной header вместо бара** - визуально интенсивнее,
   но ломает читаемость TypeChip (он тоже хочет цвет в header)

**Причины:**
- Чистое разделение сигналов: статус, тип и состояние карточки
  (idle/hover/selected) не конкурируют друг с другом
- Карточка выглядит профессионально и спокойно - доминанта
  "контент", цвет акцентируется только на edge'е
- Bar `5px` достаточно заметен для восприятия (тестовая
  верстка показывает: на 280px карточке status-bar занимает
  ~1.8% площади, но виден сразу)
- Selected и hover могут полноценно использовать ring/border
  (`indigo-500` для selected) - ничто не мешает
- Дальтоническая доступность не страдает - `StatusBadge` в
  header дополняет цвет иконкой `Check`/`AlertTriangle`/
  `XCircle`/`Circle`

**Последствия:**
- (+) Чистый визуал без conflict-of-channels
- (+) Возможно использовать contour для других целей
  (selected, drag-overlay, drop-target и т.д.)
- (+) Cohesion с дизайном панелей деталей: они тоже
  используют bar/градиент по статусу/типу - один паттерн
  на весь продукт
- (−) Нужно перевёрстывать NodeCard и адаптировать тесты
  (`NodeCard.test.tsx` проверял `border-{c}-500` классы -
  теперь проверяет `bg-{c}-500` на bar-элементе)
- (−) `STATUS_TOKENS.bg` (был `bg-{c}-50`) больше не
  используется на самой карточке - но остался в токенах для
  переиспользования в `NodeDetailsPanel.header` градиенте
  и в hover-состояниях радио-кнопок в модалках. Не
  удаляем

## ADR-016: `nodeCount`/`edgeCount` в `TopicResponse` через агрегатный SQL

**Дата:** 2026-05-07
**Статус:** принято
**Контекст:** Фронт после визуальной полировки (Этап 11) показывает
карточки тем с мини-графом и бейджем "N узлов · M связей". Бэк
до этого возвращал в `TopicResponse` только базовые поля
(id/title/description/rootNodeId/createdBy/createdAt) - счётчиков
не было. Если фронт получает их сам через запрос `/topics/{id}/graph`
для каждой темы - это N+1 (на странице со списком 6+ тем -
6+ дополнительных запросов с полным графом каждой).

**Решение:** расширить `TopicResponse` полями `nodeCount: int` и
`edgeCount: int`. Заполнять через новые методы:
- `TopicRepository.findAllWithCounts()` - один SQL с агрегатными
  LEFT JOIN-подзапросами: nodes по topic_id, edges через JOIN
  с nodes (edges не хранят topic_id напрямую - см. ADR-003).
- `TopicRepository.findByIdWithCounts(id)` - тот же SQL с
  WHERE по topic_id.
- Новый record `TopicWithCounts(Topic, int nodeCount, int edgeCount)`
  для возврата из репозитория.

`TopicService` получил методы `listTopicsWithCounts()` и
`getTopicWithCounts(id)`. Старые `listTopics()`/`getTopic(id)`
сохранены - используются в createTopic для возврата самой темы
без необходимости считать агрегаты.

`DtoMappers` получил перегрузки `toResponse(Topic)` (counts=0,
для legacy-вызовов из createTopic), `toResponse(Topic, int, int)`
и `toResponse(TopicWithCounts)`.

`TopicController`:
- `POST` - после транзакции createTopic делает второй SQL через
  `getTopicWithCounts(id)` и возвращает с counts (1 узел = root,
  0 рёбер). Семантически честно
- `GET /topics` - использует listTopicsWithCounts (один SQL для
  всех тем)
- `GET /topics/{id}` - findByIdWithCounts

**Альтернативы:**
1. **Считать на фронте через `/graph` per topic** - N+1 запросов,
   плюс на /topics-странице тяжёлый payload (полный граф ради
   двух чисел)
2. **Отдельный эндпоинт `/topics/{id}/counts`** - дополнительный
   round-trip + ещё один путь в API. Пользу не оправдывает
3. **Денормализация - хранить counts в таблице topics** -
   пришлось бы триггерить обновление на каждом insert/delete
   nodes/edges. Дорого по сложности (триггеры или application-level
   bookkeeping), profit маленький
4. **Включить counts в TopicResponse через агрегатный SQL**
   (выбрано) - один SQL для list, второй для one, третий для
   POST-create (вызывается после транзакции). Honest semantics,
   нет N+1, нет денормализации

**Причины:**
- Фронт получает всё что нужно для карточки темы одним
  запросом - простой UX
- Не вводим денормализацию (риск рассогласования счётчиков
  с реальностью)
- Один SQL для list - выполняется один раз для любого
  количества тем
- TopicWithCounts как промежуточный record позволяет ясно
  разделить "просто Topic" (для создания/обновления) и
  "Topic с агрегатами для UI" - SRP

**Последствия:**
- (+) Фронт-код для TopicListPage упрощается - данные
  пришли вместе с темой
- (+) Один SQL для list масштабируется лучше чем N+1
- (+) Семантически честные значения на всех endpoint-ах
  (включая POST)
- (−) `TopicResponse` стал шире (на 2 int поля - cheap)
- (−) POST `/topics` делает дополнительный SELECT после
  транзакции (один лишний round-trip к БД, но не запрос
  к графу - дёшево)
- (−) Открытый вопрос: `statusCounts: Map<NodeStatus, int>`
  для раскраски мини-графа на карточке темы. Сейчас
  не добавляется - мини-граф во фронте делается
  декоративным (без зависимости от status-распределения).
  Если пользователь захочет акцент по статусам тем - добавим
  отдельным агрегатом и расширим DTO. Откладывается до
  явного запроса

## ADR-017: Объединение `Source`+`Authority` под одной точкой привязки к узлу

**Дата:** 2026-05-08
**Статус:** принято (заменяет ADR-002 в части привязки `Authority` к узлу;
master-data сущность `Authority` сохраняется)
**Контекст:** ADR-002 зафиксировал две независимые привязки к узлу -
`node_sources` (источник + цитата) и `node_authorities` (учёный + stance
HOLDS/OPPOSES/NEUTRAL). На практике это породило дублирование смысла
в UI и онтологическую путаницу: при разборе исламских вопросов
"учёный X считает Y" и "это написано в книге Z автора X" описывают
**один акт цитирования**, а не два.

Конкретные проблемы текущей модели:
- На узле отображались две секции «Источники» и «Авторитеты», между
  которыми пользователь не понимал связи: «Ибн Таймийя (за)» отдельно
  и «Иктида ас-сырат» отдельно - это две привязки или одна?
- `Stance` (`HOLDS`/`OPPOSES`/`NEUTRAL`) дублировал семантику направления
  ребра. Если `CLAIM` гласит «мавлид дозволен» и к нему привязан
  Ас-Суюти со `HOLDS` - это избыточно: сам факт привязки к этому `CLAIM`
  через `Source` уже выражает позицию учёного
- На узле `QUESTION` секция авторитетов семантически невалидна: вопрос
  не имеет stance, его нельзя «поддержать» или «опровергнуть» (см.
  предшествующее обсуждение перед этим ADR)
- Невозможно было модерировать «реальность цитирования» как единое
  утверждение - пара (учёный, книга, страница, цитата) распадалась
  на две слабо связанные сущности

**Решение:** ввести трёхуровневую модель цитирования с **одной**
точкой привязки к узлу.

1. `Authority` остаётся как **master data** (нормализованный справочник
   учёных) - но **больше не привязывается к узлу напрямую**
2. `Source` (труд) приобретает опциональное поле `authority_id`
   (`FK → authorities`, `NULLABLE`) - указывает автора труда. Для
   самодостаточных источников (`QURAN`, анонимные тексты) поле остаётся
   `NULL`
3. `NodeSource` (привязка) расширяется опциональным полем `location`
   (страница / том+страница / номер хадиса / сура:аят) - точное место
   в источнике, где находится цитата
4. Таблица `node_authorities` удаляется. Enum `Stance` удаляется.
   Эндпоинт `/api/v1/nodes/{id}/authorities` (POST/GET/DELETE) удаляется
5. Эндпоинт `/api/v1/authorities` (CRUD master data) сохраняется -
   используется для выбора/inline-создания `Authority` при создании
   `Source`

С точки зрения user-experience: на узле остаётся **одна секция «Цитаты»**.
Каждая цитата визуально объединяет три уровня: автор (`Authority`) +
труд + место (`Source.title` + `NodeSource.location`) + сама цитата
(`NodeSource.quote`).

**Альтернативы рассмотрены:**

1. **Оставить модель ADR-002 как есть** - две независимые привязки.
   Минусы описаны в контексте: дублирование, концептуальный шум, проблема
   с QUESTION-узлом
2. **Полное удаление сущности `Authority`** - класть имя автора строкой
   в `Source`. Минусы: дублирование автора в каждом труде, проблема
   разной транслитерации («Ибн Таймийя» vs «Ибн Теймия»), невозможность
   фильтровать по эре/мазхабу, отсутствие master-data модерации учёного
3. **Сохранить `Authority` на узле, но удалить `Stance`** - чисто
   косметическая правка. Не решает дублирования с `Source` (та же
   проблема: «Ас-Суюти» отдельно, «Хусн аль-максыд» отдельно)
4. **Трёхуровневая модель с одной привязкой к узлу** (выбрано) - `Authority`
   нормализованный справочник, `Source` ссылается на `Authority`, узел
   привязывается только к `Source`. Сохраняет преимущества нормализации
   при чистой UX-семантике

**Причины:**

- **Соответствие классическому формату цитирования в исламской науке.**
  В `أصول الفقه` (усуль аль-фикх) сила цитаты определяется тремя
  факторами: **кто** сказал (учёный), **где** сказано (труд + точное
  место), **что** именно сказано (формулировка). Это структура
  `حجية النقل` (худжия ан-накль) - три уровня атомарных утверждений.
  Трёхуровневая нормализация ровно её отражает
- **Stance дублирует семантику ребра графа.** Если `CLAIM`
  «мавлид дозволен» и к нему привязан Ас-Суюти - сам факт привязки
  к этому `CLAIM` уже несёт информацию «учёный поддерживает». Хранить
  `stance` отдельно избыточно
- **QUESTION-узел не имеет stance в принципе.** Вопрос - это констатация
  проблемы, не утверждение. Авторитеты к нему семантически не клеятся
  (см. дискуссию перед этим ADR)
- **Модерация эффективнее в иерархии.** Модератор подтверждает учёного
  один раз, его книгу один раз, конкретную цитату на каждом attachment.
  Три уровня доверия каскадом
- **UX упрощается.** Одна секция «Цитаты» на узле вместо двух. Карточка
  цитаты собирается из трёх таблиц одним JOIN-ом

**Последствия:**

- (+) Семантически чистая модель: один акт цитирования = одна
  привязка к узлу
- (+) Нормализация авторов сохранена: один `Authority` → много `Source`,
  один `Source` → много `NodeSource` (M:1, M:N через node)
- (+) `QUESTION`-узлы теперь не имеют ни секций «источники»/«авторитеты»
  на UI (логика на фронте: `nodeType == QUESTION` → секция не
  рендерится). Бэк-валидация явная не вводится - фронт не показывает
  кнопку, бэк остаётся либеральным к атомарным операциям
- (+) Модерация работает на трёх уровнях: учёный, труд, цитата
- (+) `location` (страница/номер хадиса) теперь явное поле, а не часть
  свободного `context`
- (−) Breaking change в API: эндпоинты `/api/v1/nodes/{id}/authorities`
  (POST/GET/DELETE) удаляются. Фронт-клиенты, использующие эти
  эндпоинты, перестают работать. На текущем этапе клиент один (наш
  React-фронт), миграция контролируема
- (−) Schema-миграция теряет данные: существующие записи `node_authorities`
  не переносятся в новую модель автоматически (нет однозначного
  правила слияния `(node, authority, stance=HOLDS)` с
  `(node, source)`). Старые демо-графы (включая мавлид) пересоздаются
  через seed-скрипт. На MVP объёме данных приемлемо
- (−) `Stance` enum удаляется - семантику OPPOSES, если она нужна,
  выражает `REFUTES`-edge на родительский узел. Это совместимо с
  ADR-010 (матрица допустимых пар)
- (−) Поле `Source.authorityId` опциональное (`NULL` для `QURAN` и
  анонимных текстов) - валидация обязательности по `sourceType` пока
  не вводится, оставляем на usage-discipline в фронте
- (−) ADR-002 устаревает в части «`Authority` привязывается к узлу».
  Сама сущность `Authority` как master data сохраняется (это в ADR-002
  по-прежнему актуально)

**Будущие расширения (не делаем сейчас):**

- Жёсткая валидация `Source.authorityId` для `BOOK`/`ARTICLE`-типов
  (когда модерация будет полноценно реализована)
- `إسناد` (иснад) - цепочка передатчиков для хадиса как ordered list
  `Authority`. Расширение через таблицу `source_isnad(source_id,
  authority_id, position)`. Открытый вопрос - откладывается до явного
  запроса от пользователя
- `تعليقات` (таʿликат) - комментарии других учёных к конкретной цитате.
  Расширение через `node_source_comments(node_source_pk, source_id,
  quote)` - тот же принцип атомарного цитирования, рекурсивно

## ADR-018: Pivot из «argument-map MVP» в «платформу для исламской науки»

**Дата:** 2026-05-08
**Статус:** принято

**Контекст:** До этого решения проект двигался как single-purpose
приложение - argument-map. В Сессии 19 (frontend) выполнялась
адаптация под ADR-017 (трёхуровневая модель цитирования). При
обсуждении следующих шагов вылез фундаментальный gap: **ручной
ввод `quote` в форме привязки** - пользователь вынужден переписывать
из книги/PDF в текстовое поле. Это противоречит самой сути проекта
(точная атрибуция источников) - переписывание гарантирует ошибки.

Дискуссия привела к более широкому видению: цель не «инструмент
argument-mapping», а **платформа цифровых инструментов для
исламских учёных и студентов** с library как фундаментом. Argument-map
- одно из приложений на этом фундаменте, не центральный продукт.

**Решение:** перепрофилировать проект из single-app в платформу.

1. **Документ vision** (`docs/vision.md`) фиксирует целевое видение:
   - Платформа для исламских учёных и студентов
   - Главный принцип - точная атрибуция (учёный + труд + место)
   - Library (книги + цитирование) как фундамент
   - Приложения поверх library: argument-map (текущий), Q&A
     (следующий), будущие
2. **Документ architecture-platform** (`docs/architecture-platform.md`)
   фиксирует целевую архитектуру:
   - Monorepo с pnpm workspaces (`apps/*` + `packages/*`)
   - Один Spring Boot backend, **доменные пакеты** (`argumentmap`,
     `library`, `citation`, `qa`, `shared`)
   - Универсальная сущность `Citation` с привязкой к book-page или
     image-region; `NodeSource`/`NodeCitation` как контекстные
     обёртки в конкретных приложениях
   - Library поддерживает три способа добавления контента: парсинг
     внешних (shamela, quran.com, sunnah.com), upload PDF/EPUB,
     upload image-сканов с OCR (Tesseract)
3. **Argument-map переключается в режим support** - Этап 13 завершается
   на 13.c.1 (поле location). 13.c.2 (author-picker) и 13.d (seed)
   признаются wontfix - устаревают с приходом library: авторы будут
   резолвиться через `Book.authority`, цитаты выбираться через
   общий `CitationPicker`, не ручной ввод
4. **Репозиторий остаётся текущий** (`argument-map`) -
   переименование возможно позже (low priority)

Конкретный план миграции с текущей структуры на платформенную - в
roadmap.md как Этапы 14-19 (постепенный переход, не один большой
refactor).

**Альтернативы рассмотрены:**

1. **Продолжать argument-map MVP до полного завершения** (отвергнуто)
   - Не решает основной gap (ручной ввод цитат), и приходит к
     тому же fork-моменту через несколько этапов с большей
     накопленной debt-стоимостью
2. **Создать новую репу для платформы, текущую заархивировать как
   v1 proof-of-concept** (отвергнуто) - двойной git-history,
   потеря continuity ADR/progress документации, перенос artifacts
   (CLAUDE.md, scripts, gotchas) - extra работа без явной пользы.
   18 ADR с обоснованиями архитектурных решений теряют связь с
   живым кодом
3. **Микросервисы вместо modular monolith** (отвергнуто) -
   сложность distributed transactions, gateway, service-discovery
   до того как у нас есть пользователи. Modular monolith
   эволюционирует в микросервисы при необходимости
4. **Pivot в платформу с реструктуризацией в текущей репе**
   (выбрано) - сохраняет git-history, документацию, моё memory
   (Claude Code), быстрее начать. Имя репо - technical id, имя
   платформы - в README

**Причины:**

- **Ручной ввод цитат - архитектурный смок-тест** проекта. Если
  даже основной use-case требует переписывания (что вводит ошибки
  и трение), проект не отвечает своей цели. Library - единственный
  способ это решить
- **Платформенная природа задач Абдулы** - изначально в дизайн-
  референсе (`frontend/design-reference/`) уже были источники для
  будущих фич: source-pickers Quran/Hadith/Books, sanad explorer,
  bilingual cards. Все они зависят от library. Сделать
  argument-map + добавить library постфактум хуже чем заложить
  library правильно с начала
- **Continuity документации** оправдывает остаться в текущей репе.
  ADR-001 до ADR-018 описывают принятые решения с обоснованиями -
  при дилеммах будущих этапов (какую модель данных взять, как
  валидировать) ссылки на эти ADR работают только если они в той
  же репе

**Последствия:**

- (+) Чёткое видение - больше нет бессмысленного «продолжать
  argument-map ради завершения». Все будущие усилия идут на
  библиотеку и приложения поверх неё
- (+) Roadmap получает структуру: Этапы 14-17 фундамент library,
  Этап 18 интеграция argument-map с library citation, Этап 19+
  Q&A приложение, далее open list
- (+) Архитектурные решения (один backend, monorepo workspaces,
  доменные пакеты) зафиксированы заранее - меньше re-design'а в
  будущих сессиях
- (+) Memory Claude Code остаётся валидной (один путь), вся
  документация под рукой
- (−) **Argument-map "недоделан"** в смысле что 13.c.2 и 13.d
  были запланированы. Принимаем: эти задачи устаревают с
  library, делать их = впустую тратить время. Текущее состояние
  argument-map (демо с ручным quote) достаточно для proof
- (−) **Срок до полезного MVP вырастает** - библиотека гораздо
  больше argument-map, MVP с подключенной библиотекой через
  argument-map + Q&A это месяцы работы. Принимаем: это правильный
  путь, поспешный argument-map MVP без library не имел бы
  ценности
- (−) **Стэк расширяется** (Apache Tika, Tess4j, MinIO, react-pdf)
  - больше зависимостей, больше точек отказа. Принимаем: эти
  библиотеки стандарты в своих доменах, alternatives хуже
- (−) **Имя репозитория не отражает суть** (`argument-map`) -
  принимаем как technical id. Платформа называется в `vision.md`
  и README, без ребрэндинга git-репо

**Связь с другими ADR:**

- **ADR-017** (трёхуровневая модель цитирования) остаётся валидным
  и встраивается в новую архитектуру. `Source.authorityId` будет
  использоваться при импорте книг (book.authority - это author
  труда). `NodeSource.location` остаётся для текстовой ссылки
- **ADR-005** (монорепа) остаётся валидным - но теперь монорепа
  структурирована как platform (apps/* + packages/*), не просто
  «backend/ + frontend/»
- **ADR-008** (React 19 как frontend stack), **ADR-009** (React
  Flow для графа), **ADR-010** (матрица семантики связей) - все
  валидны для argument-map как одного из приложений

## ADR-019: Library как доменный пакет, универсальный Book с дискриминатором
**Дата:** 2026-05-08
**Статус:** принято
**Контекст:** Этап 14 - закладка фундамента платформы. Нужно решить:
(а) куда физически кладётся код library в backend, (б) как устроена
доменная модель книги - универсальная с дискриминатором или
специальные таблицы для Корана / хадис-сборников / классических
трудов

**Решение:**

(1) **Доменный пакет `ru.basnukaev.argumentmap.library.{domain,
repository,service,web}`** - первый случай новой структуры,
описанной в `architecture-platform.md`. Существующий код
(argument-map - topics/nodes/edges) остаётся плоско в корне пакета.
Постепенная миграция по мере дотрагивания, отдельный refactor не
делаем сейчас

(2) **Префикс таблиц `lib_*`**: `lib_books`, `lib_chapters`,
`lib_pages`, `lib_image_regions`. Существующие `topics/nodes/edges`
переименуются в `arg_*` отдельной миграцией позже

(3) **Универсальный `Book` с `book_type` discriminator + `metadata`
jsonb** - вместо специальных таблиц для разных типов книг. Типы:
`QURAN`, `HADITH_COLLECTION`, `BOOK`, `ARTICLE`, `MANUSCRIPT`.
Тип-специфичные поля (например, для Корана - количество сур, для
хадис-сборника - количество хадисов) хранятся в jsonb с GIN-индексом

**Альтернативы рассмотрены:**

A) **Отдельные таблицы для каждого типа** (`quran_books`,
`hadith_collections`, `regular_books`) - отклонено. Преимущества
(типизация на уровне БД, специфичные индексы) перевешиваются
недостатками: dispatch при чтении (где искать книгу по id?), много
таблиц с одинаковыми полями (title/authority/language), сложнее
универсальный list-эндпоинт «все книги». Симметрично существующему
`Source` (ADR-002), который тоже использует `source_type` + jsonb

B) **Полностью схема Корана отдельно с таблицами `quran_surahs` /
`quran_ayats`** - отклонено для MVP. Аргумент «у Корана фиксированная
структура 114 сур × N аятов» валиден, но в первую итерацию
достаточно представления Книга-Глава-Страница с разметкой через
metadata (пометка «sura: 2, ayat_range: 1-286»). Если выявится
конкретный паттерн доступа который трудно эффективно выразить через
jsonb (например, частый поиск по сура+аят с производительностью >
GIN-индекс) - выделим в отдельной миграции с собственным ADR

(4) **`authority_id` в `lib_books` опционален**. Для Корана автор
отсутствует. ON DELETE SET NULL - удаление учёного из справочника
не сносит каскадно его труды (как в ADR-017 для Source)

(5) **Иерархия глав через self-FK `parent_chapter_id`** - дерево
собирается на сервисе из плоского `findByBookId` с группировкой по
parent. Альтернативой был nested-set / closure-table, отклонено как
overkill для типичной книги в десятки-сотни глав

(6) **Координаты `ImageRegion` нормализованные (0..1)**, не
пиксельные. Это убирает зависимость от dpi скана и позволяет
рендерить регион на любом разрешении. CHECK constraint гарантирует
что прямоугольник внутри страницы

**Причины:**
- Симметрия с существующим Source / source_type / metadata - один
  паттерн в проекте, читается единообразно
- YAGNI - специальные таблицы для типов книг можно сделать когда
  выявится конкретная необходимость
- Расширяемость - новый тип книги (например, `FATAWA_COLLECTION`)
  это просто добавление значения в CHECK constraint, без миграции
  схемы
- Префикс `lib_*` явно отделяет домен от существующих таблиц,
  готовит почву для будущей реструктуризации

**Последствия:**
- (+) Минимальная схема (4 таблицы) покрывает все типы книг
- (+) Один CRUD-набор эндпоинтов работает универсально
- (+) Метаданные через jsonb - расширяемо без миграций
- (+) Готовая основа для shamela parser (Этап 15) - книга парсится
  в Book + Chapter + Page; для PDF (Этап 16) - тот же контракт;
  для image-сканов (Этап 17) - используется Page.image_url +
  ImageRegion
- (−) Type safety на уровне БД слабее чем при отдельных таблицах
  - валидируем на сервисе. Принимаем
- (−) При переходе на специализированные таблицы (если понадобится)
  потребуется data migration. Принимаем как стоимость отложенного
  решения

**Связь с другими ADR:**
- **ADR-002** (Source/Authority как справочники) - тот же паттерн
  применён к Book
- **ADR-017** (трёхуровневая модель цитирования) - после Этапа 18
  Source с book_id будет привязываться к library.Book
- **ADR-018** (платформенный pivot) - этот ADR реализует один из
  пунктов решения о доменной структуризации

## ADR-020: Импорт shamela через её desktop-API + двухслойная staging-схема
**Дата:** 2026-05-09
**Статус:** принято
**Контекст:** Этап 15 - наполнение библиотеки классическими исламскими
трудами с shamela.ws. Изначальный план (Этап 15 в roadmap до пересмотра) -
HTML-парсинг через `jsoup`. На старте сессии 21 выяснилось что
shamela.ws под агрессивным Cloudflare managed challenge:
- прямой `curl`/`WebFetch` → 403 на любом User-Agent
- `flaresolverr v3.3.21` пробивает главную страницу через прокси, но
  страницы книг (`/book/X`) задают challenge которого Chromium-120 не
  решает за 280с
- `flaresolverr v3.4.6` (Chromium 142) имеет регрессию: возвращает
  пустой HTML body на любые URL в WSL2-окружении

В параллельной сессии mitmproxy на desktop-клиенте shamela 4 был
выполнен полный реверс-инжиниринг внутреннего API. Получены 6 рабочих
endpoints, статический api_key, структура zip-архивов и SQLite-схемы
master-каталога и контента книг. Cloudflare на этих хостах прозрачен -
desktop-клиент дёргает как обычный HTTP, без challenge.

**Решение:**

(1) **Импорт через официальное desktop-API**, а не через HTML-парсинг
сайта `shamela.ws`. Endpoints:
  - `GET dev.shamela.ws/api/v1/patches/master?version=N&api_key=...` -
    мета каталога (URL дельты-zip)
  - `GET dev.shamela.ws/api/v1/patches/master-download/master-{from}-{to}.zip`
    - zip с тремя SQLite (`category`, `author`, `book`)
  - `GET dev.shamela.ws/api/v1/patches/book-updates/{id}?major_release=X&minor_release=Y`
    - URL snapshot книги
  - `GET ready.shamela.ws/books-store/{id}-{major}.zip` - полный
    snapshot книги (один SQLite с content+titles)
  - `GET ready.shamela.ws/pdf{relativePath}` - lazy PDF (по
    запросу, путь из `book.pdf_links.files[N]`)

api_key статический (`7b9524-8fc30c-e6241o-a0167e-a6d013`),
без подписи, без сессии. Бинарные endpoints на `ready.shamela.ws`
вообще не требуют ключа (раздаются как публичная статика).

(2) **Двухслойная схема в Postgres:**

  - **Слой 1 - staging:** `lib_shamela_*` таблицы (миграция 17)
    зеркалят transport-формат shamela (`category`, `author`, `book`,
    `page`, `title`, `sync_state`). Импорт SQLite → INSERT в эти
    таблицы происходит as-is, с минимальной трансформацией (TEXT→
    Long/Integer/Boolean через `SqliteValueParser`)
  - **Слой 2 - целевая модель:** `ShamelaToLibraryMapper` отдельным
    шагом проецирует `lib_shamela_book/page/title/author` в наши
    `lib_books`/`authorities`/`lib_chapters`/`lib_pages` (созданные
    миграциями 16/8). Здесь живёт логика «одна shamela-категория →
    несколько Authority с резолвом по имени», «shamela page-id-int
    → lib_pages.id-uuid», «shamela title-tree → lib_chapters»

(3) **Только полные snapshot книг** (`books-store/{id}-{major}.zip`).
Patch-формат (`ready/{id}-{major}-{minor}.zip` с LZMA+Lucene 9.5)
**отвергнут на MVP** - требует `commons-compress` и `lucene-core`,
content сидит в Lucene-индексах а не SQLite. Major-release зашит в
URL детерминированно: достаточно `lib_shamela_book.major_release`
из master, ходить за `book-updates` не нужно

(4) **Стэк:** `java.net.http.HttpClient` (Java 21 встроенный) +
`sqlite-jdbc 3.45.3.0` (новая зависимость, единственная). Никаких
WebClient, RestTemplate, OkHttp, jsoup, flaresolverr. Для HTTP
четырёх endpoints стандартный клиент Java 21 достаточен

(5) **PDF lazy**, не batch-импорт. 8500 книг × ~5MB = 40+ GB - явно
не для MVP. `fetchPdf(bookId, fileIndex)` - отдельный admin-endpoint,
парсит `pdf_links` из соответствующего `lib_shamela_book.pdf_links`,
качает на запрос, опционально кеширует на диск/MinIO

(6) **SQLite-чтение изолировано от основного `DataSource`.** Для
shamela-архивов открываем временный `DriverManager.getConnection
("jdbc:sqlite:...")`. После ETL в Postgres - закрываем connection
и удаляем zip+sqlite файлы. Нет смешения с `JdbcTemplate` основной БД

**Альтернативы рассмотрены:**

A) **HTML-парсинг через jsoup напрямую** - отвергнуто.
   `shamela.ws/book/X` под CF managed challenge, не пробивается ни
   curl, ни WebFetch
B) **HTML-парсинг через flaresolverr** - отвергнуто. Главную shamela
   проходит, страницы книг - timeout 280с. См. progress.md Сессия 21
   попытки 1-7
C) **ZenRows/ScrapingBee/Bright Data API** - платно ($50+/мес),
   внешняя зависимость, нужен api-key. Overkill для MVP когда есть
   рабочее официальное API
D) **Один слой - shamela-данные сразу в `lib_books`/`authorities`** -
   отвергнуто. Теряется possibility incremental sync (нужен
   `master_version`), теряется tombstone-семантика (`deleted_at`),
   нет audit trail откуда импортировано
E) **Patch-формат `ready/{id}-{major}-{minor}.zip`** с LZMA + Lucene 9.5
   - отвергнуто на MVP. Дополнительные зависимости (`commons-compress`,
   `lucene-core`) ради инкрементальных обновлений тогда когда мы
   ещё не закрыли первый импорт. Полные snapshot стоят дешевле и
   достаточны для bootstrap
F) **shamela offline `.bok` формат** - отвергнуто. Пришлось бы
   реверсить closed binary формат. Текущее API работает out-of-the-box

**Причины:**

- **API стабильнее HTML.** desktop-клиент shamela 4 имеет тысячи
  установок, контракт API стабилен по необходимости совместимости.
  HTML-страницы могут меняться при любом редизайне сайта
- **CF прозрачен на этих хостах** - shamela не блокирует свой
  desktop-канал, иначе все клиенты сразу сломаются
- **Структурированные данные.** SQLite даёт типизированные таблицы
  с `category`/`author`/`book`/`page`/`title` сразу. Не нужно
  парсить CSS-селекторами и угадывать какие div'ы стабильны
- **Двухслойная схема будущепроофна.** Когда придёт время
  incremental sync (Этап 15.x), `master_version` и `deleted_at`
  уже на месте. ETL-логика в `ShamelaToLibraryMapper` локализована
- **Минимум зависимостей.** java.net.http + sqlite-jdbc. Альтернативы
  тянут lucene-core, commons-compress, headless Chromium-images

**Последствия:**

- (+) Нет HTML-парсинга, нет CF challenge, нет headless browser
- (+) Реверс-инжинированный API даёт 8589 книг каталога + on-demand
  PDF из ~всего корпуса
- (+) Incremental sync architecture (`master_version` + `deleted_at`)
  готова с первого дня - инкрементальные обновления добавляются
  без миграции схемы
- (+) lazy PDF не нагружает диск 40GB+ при первой настройке
- (+) Изоляция staging-слоя от целевой доменной модели - можно
  переподнять mapping при изменении правил, не перекачивая данные
  с shamela
- (−) **API key статический и публичный** (виден в любом mitmproxy
  дампе любого пользователя). shamela может его инвалидировать в
  любой момент и поломать наш ETL. Принимаем как риск - конкурентов
  тоже сломает
- (−) **shamela контролирует доступность API.** Если они закроют
  desktop-канал, наш импорт перестаёт работать. Фолбэк - PDF upload
  (Этап 16) или image upload (Этап 17), независимые источники
- (−) **HTML-разметка `page.content` хранится as-is.** Это
  shamela-специфичная inline-разметка. Парсинг (extraction
  смыслового текста, сноски, аяты) - отдельный этап. На MVP в
  `lib_pages.text_content` после маппинга сохраняем raw HTML,
  читалка может рендерить или показывать `<pre>`
- (−) **Двухслойность стоит +2 таблицы** (`lib_shamela_book`,
  `lib_shamela_page` - 8500 строк × средне ~200 страниц = 1.7M
  строк в page-таблице). Disk-overhead ~1-2GB после полного импорта.
  Принимаем как стоимость аудита и incremental sync

**Связь с другими ADR:**
- **ADR-018** (платформенный pivot) - этот ADR реализует «парсинг
  внешних источников» (раздел A в `vision.md`)
- **ADR-019** (доменный пакет library) - `lib_shamela_*` таблицы это
  часть library-домена, java-пакет `library.shamela.{api,etl,
  mapping,web}`

## ADR-021: Source-first архитектура library - электронная версия как production оригинала
**Дата:** 2026-05-11
**Статус:** принято
**Контекст:** UX-проверка импортированной книги «Тафсир Ибн Касира»
(shamela id=14216) после закрытия Library shamela MVP (Сессия 23)
выявила фундаментальное расхождение между нашей моделью и моделью
оригинального источника.

На скриншоте shamela.ws показывается paginator вида `ج: المقدمة, ص: 3`
(том: المقدمة, страница: 3) и при клике на иконку PDF открывается
оригинальная отсканированная страница с реальным маркером "أ" (буква в
арабском abjad, обозначающая первую страницу предисловия). У нас на
фронте показывалось «Страница 1 / 4710» - просто плоский счётчик от 1
до количества записей в `lib_shamela_page`.

Корень проблемы: `ShamelaToLibraryMapper.mapPages` взял
`shamela_page.id` (internal counter shamela) как
`lib_pages.page_number`, **полностью проигнорировав** поля
`shamela_page.printed_page` (TEXT-маркер реального издания) и
`shamela_page.part` (TEXT том/juz'). Это значит ссылка вида «см. стр 47
тома 1 в Тафсире Ибн Касира» из argument-map узла не могла бы быть
проверена пользователем в его бумажной копии того же издания
«дар Ибн аль-Джаузи».

В этом же UX-обзоре всплыло требование которое не было сформулировано
явно при дизайне Library MVP: **электронная книга должна
*ссылаться на оригинал***. Не подменять оригинал, а указывать на
него - чтобы пользователь мог пройти по ссылке в бумажную/PDF копию и
найти ту же страницу того же издания. У shamela это сделано через
двойной paginator + кнопка «PDF» которая открывает scan конкретной
страницы.

**Решение:** принять архитектурный принцип **«electronic version is
a derivative of source, not a replacement»**:

(1) **Page-marker source-first.** Колонка `lib_pages.page_number`
оставлена как internal counter (для URL-state, navigation order,
prev/next). Добавлены три новых nullable-колонки в `lib_pages`
(миграция 19):
- `printed_page TEXT` - маркер страницы в реальном издании. TEXT
  потому что shamela хранит как TEXT и значения могут быть «1», «أ»
  (арабская буква предисловия), римские цифры. **Это то что
  показывается пользователю** в reader UI
- `part TEXT` - том/juz' для multi-volume изданий. Может быть цифрой
  ("1") или арабским словом ("المقدمة"). Nullable для однотомных
- `pdf_page_number INTEGER` - физическая страница в PDF-скане
  оригинального издания. На MVP всегда NULL (Mapper не скачивает PDF).
  Заполняется в будущем этапе PDF integration

(2) **Привязка к PDF/scan оригинала через будущий этап.** При импорте
из shamela сохраняется `pdf_links` в `lib_books.metadata` (raw shamela
json). Будущий этап (см. roadmap «Этап PDF integration», название
финализируется) реализует:
- Скачивание PDF из shamela на фронт-запрос или в bulk
- MinIO/локальная nginx-статика для хранения
- Frontend PDF viewer (react-pdf) - toggle «📕 PDF» в reader
- Region selection через `react-image-crop` поверх PDF - выделение
  координат на скане для cross-link с электронным текстом
- `lib_image_regions` (уже создан в миграции 16) - таблица под region
  координаты + extractedText, готова к использованию

(3) **Region-based citation для будущего CitationPicker.** При
выделении пользователем фрагмента текста (или региона на PDF-скане) -
CitationPicker сохраняет не только plain-text цитату, но и:
- `page_id` (наша `lib_pages.id`)
- `printed_page` snapshot («стр 47 тома 1») для отображения
- Координаты региона (если выделение на скане) -
  `lib_image_regions` запись

Это позволяет пользователю при чтении узла argument-map увидеть «стр
47 тома 1 в Тафсире Ибн Касира» и при клике перейти на оригинальный
PDF-скан той же страницы.

(4) **Sub-chapters сохранены через FK self-reference.** Параллельная
проблема из той же UX-проверки (Сессия 24) - чисто frontend bug
с double-tree-build, не архитектурная (backend hierarchy через
`lib_chapters.parent_chapter_id` работала корректно, фронт пере-
сбрасывал children из API). Зафиксировано в gotchas.md под
«Springdoc-openapi 2.x теряет self-referential property в schema».

**Альтернативы рассмотрены:**

A) **Хранить composite display-метку** `display_page_label TEXT`
   (например «ج 1, ص 5»). Mapper собирает один раз, frontend просто
   рендерит. **Отвергнуто:** теряется query-ability по part (нужен
   будет SELECT DISTINCT part для dropdown селектора томов), также
   разные локали потребуют разного формата метки. Хранение отдельных
   полей даёт гибкость

B) **Хранить compound в `lib_pages.metadata` jsonb** (gибкость,
   избегаем миграции схемы). **Отвергнуто:** для часто-выбираемых
   полей структурированные колонки эффективнее. SELECT printed_page
   через jsonb_path требует GIN индекс + сложнее SQL. Простые TEXT
   колонки с btree-индексом проще

C) **Конвертировать `printed_page` в INTEGER** (просто номер).
   **Отвергнуто:** shamela хранит как TEXT именно потому что значения
   могут быть нецелочисленными (арабские буквы предисловия, римские
   цифры в академических изданиях, многосоставные ссылки вида «1-3»).
   Жёсткое приведение к INT теряет данные

D) **Жёсткое требование PDF на импорт** - не импортировать книгу без
   PDF. **Отвергнуто:** shamela имеет много book-only записей без
   pdf_links (legacy данные, manuscripts без scan'ов). Lenient
   подход - импортируем всё, при наличии PDF связываем через
   pdf_page_number

E) **Skip миграции и сделать всё через jsonb** - не требует ALTER
   TABLE. **Отвергнуто:** колонки даёт type-safety, индексы быстрее,
   и Mapper-логика проще (просто `page.printedPage()`)

**Причины:**

- **Verifiability** - центральный принцип академической работы с
  текстами. Ссылка которая нельзя проверить в оригинале -
  бесполезна для серьёзной аргументации
- **shamela это уже source-first** - они показывают printed_page и
  имеют ссылку на PDF. Мы строим клон/расширение, должны следовать
  этому принципу или потеряем доверие пользователей
- **TEXT для printed_page** - shamela сам так хранит, type-coercion
  потерял бы данные. У нас рендеринг ТЕКСТ-маркера в RTL+naskh для
  арабских символов работает one-shot
- **Index (book_id, part)** для dropdown селектора томов - частый
  query, оптимизируется одним индексом. Index (book_id, printed_page)
  не нужен на MVP (поиск «найди стр X» делается по `page_number`
  через clamp с fallback на ближайшую)
- **pdf_page_number INTEGER nullable сейчас** - schema migration
  одна, чтобы при добавлении PDF integration в будущем не делать
  миграцию 20. Это явный YAGNI-противовес: добавляем колонку сейчас
  потому что точно знаем что она понадобится, и schema-add cheap
- **lib_image_regions уже на месте** - повезло, миграция 16 создала
  таблицу под scan-регионы под другим аргументом (для image-сканов
  рукописей). Сейчас используем её для PDF-региона тоже

**Последствия:**

- (+) **Page-display** правильный с первой UX-проверки после re-import
  книги: пользователь видит «أ المقدمة» как shamela, не «1»
- (+) **Schema под PDF готова** - pdf_page_number и pdf_links в
  metadata. Будущий этап Add PDF Viewer не требует миграции 20
- (+) **Type-safe доступ** на frontend через regenerated types.ts
  (printedPage, part). По дереву от backend Page record к frontend
  PageResponse без manual coercion
- (+) **Index на part** делает dropdown селектор томов O(unique-parts)
  query, не table-scan
- (+) **Region API frontend-ready** - lib_image_regions таблица есть,
  REST POST endpoint только нужно реализовать когда дойдём до PDF
- (−) **Legacy книги получают NULL для всех 3 полей.** Это OK,
  frontend fallback на pageNumber если printedPage отсутствует.
  Тестовая книга «Священный Коран» в БД имеет NULL после миграции 19
- (−) **Re-import 1681 (Сахих аль-Бухари) и 14216 (Тафсир Ибн Касира)**
  обязательны - они импортированы до миграции 19, в lib_pages
  printedPage/part NULL. Idempotent skip Mapper'а не обновит existing
  records, нужен DELETE + повторный POST /map-book. См. progress.md
- (−) **Существует semantic mismatch** между source-first семантикой
  и URL-state. URL `/books/{uuid}?page=1` сейчас означает internal
  pageNumber=1. Возможно в будущем стоит сменить URL на
  `?part=1&page=47` для bookmarkability «стр 47 том 1». На MVP -
  оставляем internal pageNumber для URL потому что unique и stable
- (−) **CitationPicker (Этап 18.f) откладывается до закрытия этого
  ADR**. Цитаты должны ссылаться на правильный page-marker - до
  миграции 19 пришлось бы переписывать БД при появлении этого ADR

**Связь с другими ADR:**
- **ADR-018** (платформенный pivot) - source-first это конкретизация
  «инструменты для исламской науки»: ссылки в науке должны быть
  верифицируемы
- **ADR-019** (доменный пакет library) - источник модели Page,
  расширяется без выхода за пределы пакета
- **ADR-020** (shamela ETL) - source-first данные приходят из
  shamela_page.printed_page и shamela_page.part которые уже были в
  staging-схеме, изначальный Mapper их игнорировал. Этот ADR -
  исправление того pre-выпуска
