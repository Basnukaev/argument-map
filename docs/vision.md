# Vision - платформа для исламской науки

> Единый источник истины для **что** мы строим и **зачем**. Технические детали
> «**как**» - в `architecture-platform.md`. Текущий план работ - в `roadmap.md`.
> Принятые архитектурные решения - в `decisions.md` (особенно ADR-018).

## Что это

Платформа цифровых инструментов для **исламских учёных и студентов**.
Набор приложений, объединённых общей библиотекой первоисточников
(Коран, хадисы, классические труды) с возможностью точного
цитирования.

Не «ещё один репозиторий цитат» и не «ещё одно приложение для дискуссий».
Это **фундамент** (library), на котором собираются разные
проблемно-ориентированные инструменты:

- Argument map - визуализация дискуссий со ссылками на источники
- Q&A с источниками - ответы на фикх/акыду-вопросы с прямыми
  цитатами из первоисточников
- (открытый список будущих приложений)

## Кому полезно

- **Студенту шариатских наук** - инструмент работы с цитатами при
  написании курсовых, разбор хадисов с иснадом, проверка цитирования
- **Исследователю** - визуализация позиций мазхабов по вопросу,
  cross-references между трудами
- **Имаму/преподавателю** - готовые ответы со ссылками для
  консультаций
- **Активному мирянину** - доступная навигация по первоисточникам,
  чтобы получить ответ «по шариату» с обоснованием

## Главный принцип - **точная атрибуция**

Любая цитата в любом приложении платформы должна иметь:
- Учёного-автора (`Authority`)
- Труд (`Source`/`Book`) с доступным контекстом (можно открыть
  страницу и убедиться)
- Точное место (`location` - страница, том, номер хадиса, сура:аят)
- Степень достоверности (для хадисов - `reliability`)

Это - условие доверия. Без точной атрибуции платформа
бессмысленна; цитата без источника - просто слова.

## Архитектурный принцип - **library как фундамент**

```
                    ┌─────────────────────────┐
                    │    library (книги +     │
                    │    цитирование)         │
                    │    Коран · хадисы ·     │
                    │    классические труды   │
                    └────────┬────────────────┘
                             │
              ┌──────────────┼──────────────┐
              │              │              │
       ┌──────▼─────┐  ┌────▼─────┐  ┌─────▼──────┐
       │ argument-  │  │   Q&A    │  │  будущие   │
       │   map      │  │          │  │ приложения │
       └────────────┘  └──────────┘  └────────────┘
```

Все приложения наверху не имеют **своих** копий контента -
только привязки (citations) к library. Это значит:
- Один экземпляр Сахих аль-Бухари в системе используется в десятках
  узлов argument-map, в сотнях ответов Q&A, и при этом
  пересмотром/коррекцией одной точки автор может обновить во всех
- Когда добавляется новая книга (например, новый тафсир) - она
  немедленно доступна для цитирования во всех приложениях
- Поиск «где этот аят/хадис уже использован» - реальный
  cross-application запрос

## Состав библиотеки (приоритет MVP)

В порядке важности:

1. **Коран** (`QURAN`) - аяты с навигацией по сурам, переводами
   (Кулиев и др.), таджвидной разметкой опционально. Источник
   данных: quran.com API или локальный mushaf JSON
2. **Сахих аль-Бухари + Сахих Муслим** (`HADITH`) - два главных
   сборника. Источник: sunnah.com API или dump
3. **Несколько ключевых классических трудов** (`BOOK`) - выбор
   определяется парсером shamela.ws. Например:
   - «Маджму' аль-Фатава» (Ибн Таймия)
   - «Иктида ас-сырат аль-мустакым» (Ибн Таймия)
   - «Хусн аль-максид» (ас-Суюти)
   - «Аль-Бидая ва-н-нихая» (Ибн Касир)
4. **Возможность загрузить произвольную книгу** - PDF/EPUB или фото-
   сканы (как archive.org показывает страницы), с OCR извлечением
   текста для возможности цитирования

## Способы добавления контента

Платформа должна поддерживать **минимум** три:

### A. Структурированный парсинг внешних источников
- shamela.ws - главный долгосрочно
- quran.com / sunnah.com - для канонических первоисточников
- Бэк автоматически парсит, нормализует в структуру
  `Book → Chapter → Page`, сохраняет в БД для offline-доступа и
  быстрого поиска

### B. Загрузка PDF/EPUB
- Пользователь грузит файл
- Бэк извлекает текст (для PDF - PDFBox или Apache Tika), нарезает
  по страницам
- Получается доступная для цитирования структура

### C. Фото-сканы страниц книги
- Пользователь грузит изображения страниц (как archive.org -
  каждая страница книги это JPG/PNG)
- Опционально: OCR (Tesseract с поддержкой арабского) извлекает
  текст под каждую страницу
- Цитирование может быть **двухмодальным**:
  - Через выделение OCR-текста (если OCR прошёл)
  - Через выделение **региона** на изображении (прямоугольник, как
    crop) - пользователь видит ровно тот фрагмент книги, на
    который ссылается. Текст под него можно ввести вручную или из
    OCR-результата

## Цитирование - центральный workflow

«Открыл книгу → нашёл место → выделил → процитировал в
приложение» - сценарий, который должен быть гладким во всех
приложениях.

**Технически:**
1. Пользователь открывает страницу книги в library reader
2. Выделяет текст или рисует регион на image-page
3. Кликает «процитировать» → выпадает выбор приложения и
   конкретного контекста («какой узел argument-map?», «какой
   ответ Q&A?»)
4. Создаётся объект цитирования (`NodeSource` для argument-map,
   `AnswerSource` для Q&A) с `bookId`/`pageId`/`region` или
   `textRange`/`quote`/`location`

**Что это означает архитектурно:**
- `Source` (как сейчас в ADR-017) - обобщённое понятие; для книг
  библиотеки это будет привязка к `Book` с `bookId` + `location`
- `NodeSource.quote` уже есть. `location` есть. Нужно добавить
  опциональные `bookPageId`, `textRange` (start/end character),
  `imageRegion` (x, y, width, height)
- В UI: общая компонента **CitationPicker** доступная из любого
  приложения

## Что **не** в scope

Чтобы видение оставалось реалистичным, явно очерчиваю границы:

- **Не** делаем социальную сеть, комменты, лайки, follow-систему
  - инструмент для работы, не платформа развлечений
- **Не** делаем форум/обсуждения «свободный текст» - всё структурно
  через argument-map или Q&A
- **Не** делаем мобильное приложение в первой итерации - desktop-first
  (graph и чтение книг тяжело на мобилках)
- **Не** делаем платные тарифы / подписки в MVP
- **Не** делаем переводы UI на другие языки в MVP - только русский
  + арабский для контента

## Принципы UX

1. **Содержание важнее украшений** - типографика, читаемость,
   плотность информации > анимации
2. **Арабский - first-class** - наскх-шрифты, RTL, грамотные
   переходы между LTR-UI и RTL-контентом
3. **Точность > скорости** - пользователь готов подождать пока
   подгрузится правильная цитата с правильным иснадом, vs
   получить «приблизительно» мгновенно
4. **Интуитивно для академика** - привычные термины, никакого
   жаргона стартапов («like», «share», «engagement»)

## Этапы развития

См. `roadmap.md` для текущего плана. На высоком уровне:

1. **Этап 13 (закрывается, минимально достаточный)** - привязка
   ручных цитат к узлам argument-map. Используется как demo
2. **Этапы 14-17 (фундамент library)** - доменная модель книг,
   shamela parser, PDF upload, image-pages с OCR, читалка с
   цитированием
3. **Этап 18 (интеграция)** - argument-map переключается на
   library citation вместо ручной формы
4. **Этап 19+ (Q&A приложение)** - первое полностью новое
   приложение поверх library
5. **Этапы 20+** - аутентификация, мультипользовательский режим,
   следующие приложения

## Открытые вопросы

Эти вопросы пока не решены - фиксирую как открытые на проектирование
фундамента:

1. **Лицензионность парсинга shamela.ws** - надо изучить ToS и формат
   распространения. shamela сама агрегирует open-content, но протокол
   доступа может ограничивать
2. **Хранение image-сканов** - на нашем диске (S3-like объект-store?
   локальная FS?) или ссылки на archive.org
3. **OCR-стэк для арабского** - Tesseract? Tess4j (Java) на бэке или
   tesseract.js на клиенте? Качество распознавания арабского с
   tashkeel?
4. **Многопользовательность** - кто видит чьи привязки в argument-map?
   Сейчас одна dev-сессия. После аутентификации - private/shared/
   public режимы?
5. **Внутренний поиск** - postgres `tsvector` достаточно или нужен
   ElasticSearch/Meilisearch? Для арабского - отдельная история (огласовки)
6. **Frontend workspaces tool** - npm workspaces / pnpm / yarn / Turborepo?
   (см. `architecture-platform.md` для предложения)
7. **Имя проекта** - сейчас `argument-map`, но это уже не отражает
   суть. Переименование - отдельное решение, низкий приоритет
   (можно сохранить git history с текущим именем, добавить package
   alias)
