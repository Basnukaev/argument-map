# Гигиена документации

Правила поддержания документации в порядке - чтобы через месяц
работы она не превращалась в свалку, на которую новая сессия Claude
тратит токены до того как добраться до полезного.

Каждое правило ниже - **конкретный триггер** (когда применять) и
**конкретное действие** (что сделать). Не философия, а чек-лист.

---

## Принцип 1. Single source of truth

Каждая тема имеет ровно один файл-владельца. Остальные документы
**ссылаются**, не дублируют

| Тема | Владелец |
|---|---|
| Стэк проекта | корневой `README.md` |
| Команды dev-цикла (запуск, тесты) | корневой `CLAUDE.md` |
| Conventional Commits | `docs/git-workflow.md` |
| Что и зачем строим | `docs/vision.md` |
| Целевая архитектура | `docs/architecture-platform.md` |
| Бэк-стандарты (Java/Spring/JDBC) | `backend/docs/coding-standards.md` |
| Фронт-стандарты (TS/React/Tailwind) | `frontend/docs/coding-standards.md` |
| REST контракт | `docs/api-contract.md` |
| Ловушки и обходы | `docs/gotchas.md` |
| Доменные термины | `docs/glossary.md` |
| ADR | `docs/decisions.md` |
| Активные этапы и подзадачи | `docs/roadmap.md` |
| Идеи без привязки к этапу | `docs/backlog.md` |
| Журнал сессий | `docs/progress.md` |
| Стартовый промпт для новой сессии | `docs/SESSION_START_PROMPT.md` |
| Эти правила гигиены | `docs/doc-hygiene.md` (этот файл) |

**Триггер** при правке: ловишь себя на копировании содержимого из
одного документа в другой - стоп. Поставь ссылку, не копию.
Если действительно нужно дублирование - значит источник истины
выбран неправильно

## Принцип 2. CLAUDE.md по уровням - не дублируй

- **Корневой `CLAUDE.md`** - что общее для всего репо: стэк
  одной строкой, layout, команды, ссылки на документы
- **`backend/CLAUDE.md`** - **только** бэк-специфика: Liquibase
  conventions, JDBC паттерны, что НЕ делать в Java/Spring
- **`frontend/CLAUDE.md`** - **только** фронт-специфика: TS strict
  правила, React-конвенции, что НЕ делать в TS/React

**Триггер**: если содержимое subdir CLAUDE.md применимо ко всему
проекту - перенеси в корневой и удали из subdir

**Целевой размер subdir CLAUDE.md**: ~150 строк. Если больше -
большая часть скорее всего дубликат корневого или должна стать
отдельным документом в `backend/docs/` или `frontend/docs/`

## Принцип 3. roadmap.md - сжимай закрытые этапы

Закрытый этап **не** должен оставаться развёрнутым чек-листом

**Триггер**: закрыл этап (последний `[x]` проставлен)

**Действие** прямо в том же коммите который закрывает этап:

```markdown
## Этап N. Название (закрыт Сессия M)

Одно-два предложения что было сделано. Ссылки на ADR-X / commit-hash
если есть. Детали - в `progress.md` Сессия M.
```

Развёрнутый чек-лист удаляется. Информация не теряется - она в
`progress.md` и git history

**Активные этапы** держат полный чек-лист с `[x]`/`[ ]` и
подзадачами

**Триггер для split на новый этап**: если внутри активного этапа
больше 10 подзадач **и** часть из них логически отдельна -
выделить в новый этап. roadmap.md размер: не больше ~400 строк
для активной части

## Принцип 4. backlog.md - не в roadmap

В roadmap только **этапы**: активные или недавно закрытые. Идеи
без привязки к этапу - в `docs/backlog.md`

**Триггер**: задача появляется, но не относится к текущему этапу и
не блокирует ближайшие 2-3 этапа

**Действие**: добавить в backlog.md в соответствующую секцию (Фронт
/ Бэк / UI-идеи / Responsive / Будущие фичи). Когда задача
созревает - переезжает в новый Этап в roadmap

## Принцип 5. progress.md - короткий формат + ротация

### Формат одной записи (50-100 строк максимум)

```markdown
## YYYY-MM-DD - Сессия N (scope)

### Сделано
- `<hash>` `<commit-subject>` - одна строка о *неочевидном* в коммите
  (не пересказ git log, а почему/как)
- ...

### Решения (если были)
- ADR-X принят: одно предложение почему
- ...

### Проблемы (только нерешённые)
- что открыто, что попробовали, ссылка на gotcha если есть

### Следующий шаг
- 1-2 предложения. Конкретная задача
```

**Не делай**:
- не переписывай содержимое коммитов (`git log` + `git show` дают
  это в любой момент)
- не вставляй полные diff'ы
- не пиши «работаем над X» если X не завершён - это не journal
  entry, это todo

### Архивация

**Триггер**: `progress.md` > 1500 строк или > 10 сессий с
последней архивации

**Действие**:
1. Создать `docs/archive/progress-sessions-N-M.md` (где N - первая
   сессия в архиве, M - последняя)
2. Переместить туда все записи кроме последних 3 сессий
3. В `progress.md` оставить header с указателем:

```markdown
# Журнал работы

Последние 3 сессии. Архив старых: `docs/archive/progress-sessions-N-M.md`

---
```

## Принцип 6. SESSION_START_PROMPT.md - не растёт

Структура файла **фиксированная**:

1. preamble (для чего этот файл)
2. Автономный режим (полномочия, red lines, эскалация)
3. START-OF-SESSION PROTOCOL (что прочитать первым делом)
4. Текущий приоритет (1-2 абзаца, обновляется каждой сессией)
5. Контрольные точки качества handoff'а

**Триггер**: закрытие сессии

**Действие**:
- обновить раздел «Текущий приоритет» под следующую сессию
- **не добавлять** новых разделов «КРИТИЧНО для Сессии N+»
- история сессий живёт в `progress.md`, не здесь

**Целевой размер**: 200-300 строк. Если файл выходит за 400 строк -
вылавливай дубли с CLAUDE.md / progress.md / roadmap.md и выкидывай

## Принцип 7. ADR - не редактируй старые

(подтверждение существующего правила, не новое)

- новые ADR добавляются с возрастающим номером
- старые не правятся (кроме опечаток)
- если решение отменено / заменено - **новый ADR** со статусом
  «заменяет ADR-N» / «отменяет ADR-N»

`decisions.md` растёт линейно - это **нормально**. Он архивный.
Compaction делается через `СВЁРНУТО` summary в начале если когда-то
понадобится: «ADR-001..ADR-010 - foundational, см. краткое
содержание в architecture.md»

## Принцип 8. При reorg структуры - синхронизируй всё

**Триггер**: переименование пакета / папки / реорганизация фронта
или бэка (типа cleanup marathon Сессия 25 с `src/apps/`)

**Действие** в том же коммите что reorg:
- `README.md` - layout-секция
- корневой `CLAUDE.md` - layout
- `backend/CLAUDE.md` / `frontend/CLAUDE.md` - локальная структура
- `docs/architecture.md` / `docs/architecture-platform.md`
- `docs/SESSION_START_PROMPT.md` - КЛЮЧЕВЫЕ ФАЙЛЫ секция

Грубая проверка в WSL:
```bash
grep -rn "src/pages/\|src/components/" docs/ frontend/CLAUDE.md README.md
```

если что-то нашлось после reorg - в коммите reorg есть невыполненный
шаг

## Принцип 9. Stale-entries detection

**Триггер**: завершение каждой сессии (вместе с обновлением progress)

**Действие** (1 минута):
- glance через `docs/SESSION_START_PROMPT.md` - даты и счётчики Сессий
  в реальности?
- glance через `docs/roadmap.md` - закрытые этапы свёрнуты?
- если упоминается удалённый файл / переименованный класс - исправить

## Принцип 10. memory ≠ docs

- **memory** (`~/.claude/projects/.../memory/`) - персональные
  feedback'и user'а, корректировки стиля работы. Сохраняются
  между сессиями автоматически
- **docs/** - правила, ADR, контракты, история проекта

**Разделение**: если правило про **проект** (например «не использовать
JPA») - в `backend/CLAUDE.md` или `backend/docs/antipatterns.md`. Если
про **стиль работы с этим user'ом** (например «не запускай билды на
каждый чих») - в memory

Если правило сейчас в memory но применимо к любой сессии любого
человека - перенеси в `CLAUDE.md`. Memory держит уникальные
персональные паттерны, не проектную документацию

## Принцип 11. Команды и пути - один источник

Команды dev-цикла (запуск backend/frontend, `./mvnw verify`,
`npm run build`) описаны **только** в корневом `CLAUDE.md`. Не
переписывай в каждом subdir CLAUDE.md или в SESSION_START_PROMPT

При смене порта / debug-флага - правится **одно** место

## Чек-лист в конце каждой сессии

Перед commit'ом записи в progress.md:

- [ ] roadmap.md - закрытые этапы сжаты до summary?
- [ ] SESSION_START_PROMPT.md - «Текущий приоритет» обновлён? Не
      появилось новой секции «КРИТИЧНО для Сессии N+»?
- [ ] progress.md - запись по формату, не дублирует git log?
- [ ] gotchas.md / glossary.md / api-contract.md / ADR обновлены
      если изменения требовали (см. backend/CLAUDE.md или
      frontend/CLAUDE.md чек-лист по типу коммита)
- [ ] если был reorg структуры - все упоминания путей обновлены
      (grep по docs/)
- [ ] progress.md > 1500 строк? - архивировать
- [ ] SESSION_START_PROMPT.md > 400 строк? - почистить дубли

## Когда правила нужно нарушить

Правила выше - default. Можно отойти если:
- работа экстренная (фикс прода) - сжатие документации делается
  следом отдельным docs-коммитом
- крупный refactor где временное состояние документации
  непоследовательное (например в середине этапа). Финальный
  коммит этапа приводит документацию в порядок
- user явно сказал «оставь как есть» (но он явно про конкретную
  ситуацию, не про отмену правил вообще)

В остальных случаях - применяй
